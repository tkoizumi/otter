# v0.2.0 release plan

Status: proposed. Date: 2026-09-28. Starting point: `v0.1.18` (`98df724`).

This plan turns the `v0.2.0` gate in [product-roadmap.md](product-roadmap.md)
into a sequence of concrete releases. It is a work order, not a commitment to
dates. Each release below states what it carries, what proves it, and what it
deliberately leaves out.

The findings referenced here come from a read-only source audit of `v0.1.18`.
They are **verified in source and not yet reproduced at runtime** — no test in
the repository currently triggers them. Turning them into failing tests is part
of the work, beginning with `v0.1.19`.

## Where `v0.1.18` stands

The runtime architecture is substantially ahead of its release number: durable
enqueue, an atomic claim, release-digest binding, process-group cancellation,
and a loopback auth guard all exist and are tested. What is missing is the
*evidence* that the guarantees hold under failure, and in six places the
implementation contradicts the guarantee it claims.

The load-bearing contradiction is in [architecture.md](architecture.md):
crash recovery is documented as leaving "no child processes survived the
restart" and reconciling all interrupted work. Today neither is fully true —
recovery is silently capped, and children can outlive the daemon.

`v0.1.19` and `v0.2.0` close that gap from both ends: `v0.1.19` removes the
defects that make accepted work losable, and `v0.2.0` publishes the contract and
the fault matrix that prove it.

## The decision rule

`v0.2.0` is a phase close, so it is not simply "the next batch of fixes". Two
release types carry the work:

| | Patch (`v0.1.x`) | Minor (`v0.2.0`) |
| --- | --- | --- |
| Risk | Drop-in; no schema, manifest, CLI, or API change | May change internal behavior and documented semantics |
| Contents | A defect that loses or corrupts work, or that a user can hit today | New guarantees, new test infrastructure, new contract documents |
| Evidence | A regression test that fails before and passes after | The versioned contract plus the full fault matrix |
| Reversible by | Swapping the binary back | Restoring the pre-upgrade backup, if a migration shipped |

Applying the rule: three of the six defects are patch material because they
lose accepted work and the fixes are local. The remaining three land in
`v0.2.0`: two restructure transactions or add platform-specific process code and
only mean something once the fault matrix can prove them, and the third — the
fail-closed startup hold — was deferred so the urgent truncation fix could ship
in `v0.1.19` on its own.

Do not hold a work-losing fix for the minor release. `v0.1.19` exists precisely
so that the urgent fixes are not coupled to the larger changes.

## v0.1.19 — Stop losing accepted work

**Theme.** Three defects that strand or duplicate work a user has already been
told was accepted. All three fixes are local; none changes an interface.

### 1. Recovery truncation

`recovery.go:23`, `recovery.go:74` and `daemon.go:714` all request `10000` rows,
but `List` coerces any limit above 1000 to `50` (`runs.go:339-342`). On a busy
crash, at most 50 `running` runs are recovered and at most 50 orphaned queued
runs are re-enqueued; everything beyond that stays non-terminal permanently.

The coercion is the root cause and the fix belongs there, not at the call sites.
The cleanest shape is for these callers to ask for *all* matching rows and page
internally: "every run in this status" is a semantic request, not a display
query, and it should never inherit a listing default. A minimum fix is to raise
the ceiling, but that only moves the cliff.

The truncation itself is fixed here. Making a failed recovery refuse startup —
`daemon.go:280-285` logs `recovery_failed` and starts anyway, turning one
transient error into permanently stranded runs — is defect 6, deferred to
`v0.2.0` so this read fix is not coupled to a startup-policy change; see
[Fail-closed startup hold](#6-fail-closed-startup-hold).

### 2. Claimed runs dropped

`workers.go:81-87` (`run_load_failed`) and `workers.go:166-170`
(`run_mark_running_failed`) return without terminal-ing or re-enqueueing the
run. The claim already deleted the `run_queue` row, and reconciliation only runs
at startup — so the run sits as `queued` with no queue entry until the next
restart.

The worker must leave the run in a state reconciliation agrees with: either
return it to the queue with a backoff, or record a terminal failure. Decide this
per error class — a transient DB error should re-enqueue; an unreadable run
record should terminal — and state the choice in the commit message.

### 3. Capacity slot leak

`queue.go:225-244`: `Reserve` runs inside the transaction, `withTx` commits
after `fn` returns, and a commit failure returns without `Release`. Each
occurrence permanently shrinks worker capacity — the failure mode is a daemon
that quietly runs fewer workers than configured.

Release the slot when the claim transaction fails to commit. The same applies to
any early return between a successful `Reserve` and a durable delete.

### New capability

None. This release exists to remove defects.

### Acceptance

- A regression test per defect, each failing against `main` before its fix.
- The recovery test seeds **more than 50** stale `running` runs and asserts every
  one is recovered. This is the test whose absence hid the bug.
- No schema migration ships, so `v0.1.19` downgrades to `v0.1.18` by swapping
  the binary.
- [architecture.md](architecture.md) crash-recovery section is corrected where
  it currently overstates the guarantee.

### Out of scope

The fail-closed startup hold (#6), the atomic finish/retry change (#4),
child-lifetime work (#5), the runtime contract, and the fault matrix. All five
are `v0.2.0`.

## v0.2.0 — Close Phase 1: the guarantee is published and proven

**Theme.** Finish the correctness work, then publish the contract and the
evidence that closes the roadmap's Phase 1 gate.

### 4. Finish and retry become one decision

`finishRun` commits the terminal state at `workers.go:334`, then logs, reads the
job's detail line, and notifies, before calling `scheduleRetry` at
`workers.go:399` — a separate transaction. A crash in between leaves a terminal
failed run with no retry, and `recoverRuns` only scans `running`, so nothing
repairs it. If `Finish` itself fails after a *successful* child, the run stays
`running` and is re-executed on restart.

The fix is to decide the attempt's outcome and persist it — terminal state *and*
any successor attempt, plus its queue row — in one transaction. Notification and
detail-line logging stay outside it; they are best-effort and must never affect
what the run did. A `Finish` failure after a successful child needs an explicit
resolution rather than a silent `return`.

### 5. Children must not outlive the daemon

`proc_unix.go:13-15` sets `Setpgid` but never `Pdeathsig`, and `Pdeathsig`
appears nowhere in the codebase. After `kill -9` or an OOM kill the child keeps
running while restart marks it failed and retries it: two concurrent executions
of the same work, and therefore duplicated external effects.

On Linux, `Pdeathsig` addresses the direct child; it does not cover grandchildren
and does not exist on Darwin, which is a shipped target. Complete the story with
a startup sweep for surviving process groups where the platform allows it, and
where it does not, document the exposure. If the honest answer is "orphans remain
possible on macOS", that is a legitimate way to close the gate — recorded as a
platform-specific limitation in the runtime contract, not left implicit.

**Decision (2026-09-28): option (a) — Linux `Pdeathsig`, macOS documented.** The
child launcher is split into `proc_linux.go` (`Setpgid` + `Pdeathsig: SIGKILL`)
and `proc_darwin.go` (`Setpgid` only) with the group helpers shared in
`proc_unix.go`, and the macOS exposure is stated in
[architecture.md](architecture.md#child-lifetime-is-platform-specific), closing
`OT-009`. A persisted child pgid plus a startup sweep was rejected: it is
post-crash cleanup rather than prevention, because the orphan runs between the
kill and the next start; `kill(-pgid)` is unsafe against a recycled pid without a
boot identity and a per-process identity check, neither of which ports to macOS;
and it buys no macOS coverage, which needs a supervisor or an in-child
death-watch pipe instead. It would also ship migration `0011` and therefore a
downgrade path, which this release otherwise avoids. The regression test
(`internal/executor/proc_linux_test.go`) SIGKILLs the parent process and asserts
the child dies; it fails against the pre-fix code and passes after it. macOS is
explicitly excluded from that test.

### 6. Fail-closed startup hold

`daemon.go:280-285` logs `recovery_failed` or `queue_reconcile_failed` and opens
for new work anyway. A startup that cannot repair interrupted work therefore
turns one transient database error into permanently stranded runs: a `running`
row with no queue row, no terminal state and no retry successor, invisible to the
worker pool until a later restart happens to succeed.

`New` must refuse to start when recovery or queue reconciliation fails. A
failure to repair **any** interrupted run counts, not only a failure of the
initial read: a run that could not be terminalised is precisely the stranded
work the pass exists to prevent, so its persistence error is aggregated and
refuses startup too. The one escape hatch is explicit: a new
`--allow-incomplete-recovery` flag (`OTTER_ALLOW_INCOMPLETE_RECOVERY`) starts
anyway and logs the error at `error` level, for an operator who must bring a
daemon up to inspect or repair a database it cannot read. The default is
fail-closed, because the safe failure is a daemon that stays down and visible,
not one that serves while accepted work sits stranded.

This is the narrow hold: `New` returns an error and the process exits. Binding
the API while holding admission and execution — so the failure is inspectable
through the running daemon — is the broader recovery hold in
[host-recovery-implementation-plan.md](host-recovery-implementation-plan.md) and
is not part of this release.

### New capability: the versioned runtime contract

Phase 1's exit evidence is "a versioned runtime contract and automated fault
matrix". The contract does not exist today as a document; it must be written and
it must match observed behavior.

It should pin, at minimum:

- The attempt state machine (`queued`, `running`, `succeeded`, `failed`,
  `retrying`, `cancelled`, `timed_out`) and which transitions are legal.
- What an accepted request promises: durable work or an explicit, inspectable
  failure.
- Missed cron windows (not replayed) and duplicate webhook delivery.
- State-write concurrency: `ctx.state` is a plain upsert with no compare-and-swap,
  so read-modify-write is not atomic and `concurrency: 1` is the safe default.
  Say so.
- That retries can repeat external effects, and that exactly-once execution is
  **not** promised. Idempotency guidance belongs here.
- Supported platforms, and which guarantees are platform-specific.

### New capability: the fault matrix

Today recovery is tested by seeding a `running` row with the daemon in-process
(`daemon_test.go:946-969`). That is a simulation, and it is why defect #1 stayed
invisible. This release needs a harness that can kill the daemon and the child,
with at least these scenarios:

| Scenario | Asserts |
| --- | --- |
| SIGKILL the daemon mid-run | Every interrupted run reaches a terminal state or is re-enqueued; more than 50 at once |
| SIGKILL the daemon between finish and retry | No terminal failure is left without its retry |
| Kill the child, leave the daemon | The attempt is recorded correctly and descendants do not survive |
| Crash during retry backoff | The retry is claimable after `available_at`, with backoff preserved |
| Cancel a running run | The process group dies, status is `cancelled`, and it is not retried |
| Two processes claim concurrently | No run is executed twice across processes |
| `concurrency: N` state updates | The documented concurrency behavior matches observation |
| Disk exhaustion / oversized output | Failures are visible, bounded, and recoverable |

The concurrent-claim scenario needs a second connection or process: today
`queue_test.go:312` shares the single `MaxOpenConns(1)` connection, so it cannot
detect a cross-process double claim.

### Acceptance

- All six defects fixed, each with a test that fails before it.
- The fault matrix runs in CI and passes.
- The runtime contract is published and every claim in it is backed by a matrix
  scenario. A guarantee with no test does not go in the document.
- No unresolved critical correctness failure. This is the Phase 1 gate verbatim.
- `architecture.md` matches the implemented behavior, including the macOS
  caveat if one remains.

### Out of scope

Retention, diagnostics, backup/restore, and migration visibility are `v0.3.0`.
Contract freezing and the deprecation policy are `v0.4.0`. Capacity limits and
the supported-load envelope are `v0.5.0`. Removing a defect must not wait for its
neighboring feature, and adding a feature must not delay the gate.

## Outlook past `v0.2.0`

Not part of this plan; the shape is recorded so the versions keep their meaning.

| Version | Headline work |
| --- | --- |
| `v0.3.0` | Automatic retention for run logs and releases; queue age and per-job freshness signals; migration visibility; tested backup/restore and upgrade drills |
| `v0.4.0` | Frozen manifest, SDK, CLI JSON, and API, with a compatibility and deprecation policy and contract tests; explicit supported platforms |
| `v0.5.0` | Queue admission bounds and backpressure; published supported-load envelope |
| `v0.6.0` | Pilot jobs across independent deployments; 30 days unattended |
| `v1.0.0` | Freeze: evidence bundle and compatibility commitment, no new surface |

Two corrections to existing documentation should ride along with the release that
touches the area, since both are wrong at `v0.1.18`:

- The ops guide's retention SQL filters on `runs.queued_at`, which does not
  exist (the column is `created_at`), so the documented prune job fails at
  runtime. Fix in `v0.3.0` with retention.
- The ops guide promises a `migration_applied` log line that `Migrate` never
  emits, because it has no logger and `schema_migrations` has no description
  column. Fix in `v0.3.0` with migration visibility.

## Release checklist

Applies to each release above.

1. Every fix has a regression test that failed before it.
2. `make test` and `make smoke` pass locally and in CI.
3. `gofmt`/`go vet` are clean; the release-config job passes.
4. The changelog entry (`docs/releases/<version>.md`) states user-visible
   behavior, not just "fixed bug"; it is the file the tag publishes as the
   GitHub release body.
5. Any claim the release makes is true in the shipped artifact — re-read the
   relevant doc against the behavior, do not assume.
6. If a migration shipped, the downgrade path is stated in the ops guide.
7. Tag only when the acceptance list is complete. The version number means the
   gate passed, not that the work is finished.
