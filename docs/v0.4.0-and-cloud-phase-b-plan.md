# v0.4.0 and Cloud Phase B — combined plan

Status: proposed. Date: 2026-10-02. Supersedes the sequencing in
[product-roadmap.md](product-roadmap.md) §"Sequence" and
[cloud-alpha-readiness.md](cloud-alpha-readiness.md) §17 for this track.

This plan carries two tracks that run **at the same time**:

- **Track R — the runtime**, which closes `v0.4.0`: the `CL-21`/`CL-22`/`CL-23`
  prerequisites plus the interface freeze.
- **Track C — Otter Cloud Phase B**, a small multi-tenant control plane and a
  demo-quality UI.

They share one contract. The runtime work is not a gate in front of the control
plane; it is the interface the control plane is written against, and it is the
same work whether Cloud exists or not.

## 1. The decision

**Start Phase B now, in parallel with `v0.4.0`, rather than after the Phase 3
runtime readiness gate.**

The roadmap says no cloud implementation before that gate
([product-roadmap.md:51](product-roadmap.md#L51)) and prefers the harness first
([:56–59](product-roadmap.md#L56-L59)). This plan deviates deliberately, and
records the decision (`CA-55`) so the two documents stop disagreeing.

Why the deviation is safe now:

1. **Castor is a real second consumer.** The control plane is not built
   speculatively for one demo; three production imports already run on the
   runtime ([p0-13-castor-import-migration-record.md](p0-13-castor-import-migration-record.md)).
2. **The runtime will keep changing at this stage regardless.** A hard gate
   delays the control plane without reducing the churn. The correct instrument
   is an interface contract, not a ban.
3. **UI and projections absorb churn cheaply; identity and credentials do not.**
   The plan is therefore ordered so the expensive-to-retrofit layers land first
   and the cheap-to-change layers land against them.

### The gate is reframed, not deleted

| Gate | Was | Is now |
| --- | --- | --- |
| Phase A | Blocks all of Phase B | Blocks **any paying client's production work** from being pointed at a runtime. Building, demoing and dogfooding proceed. |
| Phase 3 readiness | Blocks cloud implementation | Blocks **external/client onboarding** (`CA-01`–`CA-05`, `CA-40`–`CA-46`, `CA-50`–`CA-52`). |

Phase A remains a real gate. It is not a formality, and the plan deliberately
keeps the one promise that matters: **no paying customer's production job runs
on an unproven execution plane.**

## 2. Guardrails — what makes running the tracks in parallel safe

These are not aspirational. Each one is a rule with a test or a code structure
behind it.

1. **No runtime admin token in Cloud.** Not in the database, not in the
   environment, not in a demo config. The demo uses the `CL-21` scoped control
   credential from its first working day. `CL-21` is therefore the first runtime
   item, not a later hardening pass.
2. **Projections are rebuildable caches (`CL-05`).** Cloud stores no
   authoritative execution state. Deleting the projection and reconstructing it
   must not change what runs.
3. **Every mutating command carries an idempotency key from day one (`CL-11`).**
   A duplicated "Run now" yields one run. This is a UI-shaped correctness bug; a
   CLI user never hits it, a browser user hits it constantly.
4. **No log, trace or capture bodies in Cloud storage (`CL-12`).** The UI streams
   or proxies them from the runtime.
5. **One seam to the runtime.** All runtime calls go through a single
   `RuntimeClient` interface. Swapping credential classes or transports is a
   change in one place.

## 3. The shared contract

```text
        Otter Cloud (multi-tenant)                    Runtimes (single-tenant)
   ┌──────────────────────────────────┐          ┌──────────────────────────┐
   │ Identity / orgs        (CL-01)   │          │  otterd                  │
   │ Runtime registry       (CL-02)   │◀─────────│  · heartbeat + events    │
   │ Projections (cache)    (CL-05)   │  outbound│  · scoped control cred   │
   │ Command gateway        (CL-04)   │   events │    (CL-21)               │
   │ Idempotency + audit (CL-11/19)   │          │  · schedules (CL-22)     │
   │ Web UI                 (CL-06)   │─────────▶│  · scoped API (CL-23)    │
   └──────────────────────────────────┘  scoped  └──────────────────────────┘
                                          commands
```

Three things cross the boundary and nothing else:

- **Commands** — run, pause, resume, schedule CRUD. Cloud → runtime, authenticated
  with the `CL-21` control credential, idempotent.
- **Events** — heartbeat, job changed, run accepted/started/succeeded/failed,
  health changed. Runtime → Cloud, outbound.
- **Metadata projections** — jobs, runs, status, timings. Never log or capture
  bodies.

## 4. Track R — the runtime (`v0.4.0`)

Ordered by what unblocks the control plane. `R1` is first because guardrail 1
depends on it.

### R1 — `CL-21`, the scoped control credential

A new runtime credential class whose holder can command the gateway surface and
nothing else.

- Can: list jobs, submit a run, cancel, pause, resume, schedule CRUD, read run
  status and timings.
- Cannot: read secrets, read `ctx.state`, read capture payloads, register or
  delete jobs, change daemon configuration.
- Independently revocable per runtime; rotation is a drill.

**Done when:** a runtime issues a control credential, that credential is refused
by every non-gateway route, revocation takes effect immediately, and no code path
will accept an admin token in its place.

**Shipped 2026-10-02** — migration `0013_api_tokens`, `internal/apitoken`,
`otter token create|list|revoke`. Two scopes exist, `read` and `control`,
alongside the admin token, which stays the static `OTTER_API_TOKEN` so a database
compromise cannot mint it. Only a SHA-256 is stored, and the row is read on every
request, so revocation takes effect on the next one with no restart. The
route-by-route boundary is the table in
[api-reference.md](api-reference.md#scoped-api-tokens), asserted by
`internal/api/token_scope_test.go` and `internal/apitoken/store_test.go`.

Two consequences for the rest of this plan. The credential is narrower than
`CL-04`'s gateway list in exactly two deliberate places: capture *payloads* stay
admin-only (the summaries do not), and a scoped caller's merged timeline omits
HTTP entries. And `CL-01`/`CL-02` can now be built against a credential that
exists rather than a placeholder.

### R2 — `CL-22`, dynamic schedules, completed

[v0.3.0](../CHANGELOG.md) shipped phase 1–3a: a `job_schedules` table with **one
row per job**, the store-backed scheduler, and `PUT`/`DELETE
/v1/jobs/{id}/schedule`. What remains is
[dynamic-schedules-design.md](dynamic-schedules-design.md) phases 3–5:

- `schedule_id`-keyed endpoints: list, create, get, patch, delete, pause, resume
  ([§9](dynamic-schedules-design.md#L286)).
- Per-occurrence payload (`ctx.trigger` carries it).
- Idempotency keys on create; duplicate command produces no second schedule.
- `schedule_fires` for exactly-one-run-per-occurrence across restarts.
- UTC pinned everywhere, with the manifest's local-time meaning documented as a
  change.
- Manifest reconciliation: a manifest-owned row refuses API mutation with `409`.
- CLI family: `otter schedule list|add|update|remove|pause|resume`.

**Done when:** a runtime behind an inbound-deny firewall is given a new schedule
by Cloud, the occurrence fires with its payload, a restart neither replays nor
drops it, a duplicate command produces no second schedule, and `otter reload`
leaves an API-created schedule untouched.

### R3 — `CL-23`, the API as a supported remote surface

Five deliverables, in the order that unblocks a remote client
([dynamic-schedules-design.md §9.1](dynamic-schedules-design.md#L286)):

1. ~~Scoped operator tokens: control, read, admin; multiple named tokens with
   rotation and revocation.~~ **Shipped with R1**: named tokens with `read` and
   `control` scopes, and immediate revocation. A named *admin* token is
   deliberately not offered — full authority stays `OTTER_API_TOKEN`.
2. `otter deploy` accepts a non-loopback bind behind an explicit opt-in, with a
   warning, instead of refusing.
3. TLS: either direct support or a documented reverse-proxy pattern.
4. `assert-host-permissions.sh` asserts the *configured* posture (loopback, or a
   token with an expected bind/CIDR) rather than hardcoding loopback — and
   `P0-07`'s recorded host evidence is **re-run**, not amended.
5. Reconcile [security.md](security.md) and `CL-04`'s inbound-access wording.

**Done when:** a runtime on a private network behind TLS is operated from another
host by a client holding a read-only token that cannot execute code, and the host
assertion passes on that configuration without weakening the loopback default.

### R4 — the `v0.4.0` interface freeze

- A written compatibility and deprecation policy for the manifest schema, the
  Python SDK, CLI JSON, and the HTTP API.
- Versioned, machine-readable JSON envelopes for the commands and endpoints
  scripts and Cloud consume.
- The platform contract: supported OS and architectures; everything else marked
  unsupported.
- The honest limits published in
  [runtime-contract.md](runtime-contract.md): update concurrency, retry effect
  duplication, downgrade support, transport security.

**Done when:** the policy is published, contract tests pin each frozen interface,
and every documented limit matches observed behaviour.

### R5 — carry-forward runtime hygiene

Small items that specifically threaten fleet operation, pulled into this release
rather than `v0.5.0` because the control plane depends on them:

- `OT-010` — daemon-side release pinning check before retention (a submit can
  currently race retention).
- `OT-024` — tie the CloudWatch metric contract across `otter` and
  `otter-platform` to one generated constant or a checked assertion.
- `OT-029` — a retired job whose source is still in the repo must not fail a
  full `otter deploy`; the release step must skip and report a refused path.

**Done when:** each has a failing-before regression test.

## 5. Track C — the control plane

Scope is the minimum that makes the demo honest and the paying-customer version
reachable without a rewrite.

### C1 — Identity and tenancy (`CL-01`)

`User`, `Organization`, `OrganizationMembership`, `Runtime`,
`RuntimeCredential`. Every request is authorized against the organization.

For the demo, authentication is deliberately simple but **real enough to show
scoping** — an email session with one seeded organization (Castor) and a second
org holding nothing, so cross-tenant refusal is demonstrable.

**Done when:** a cross-tenant authorization test proves org A cannot read or
operate org B's resources.

### C2 — Runtime registry and fleet health (`CL-02`, `CL-07`)

Stable runtime id, organization ownership, version, last heartbeat, connection
status. A runtime authenticates only as itself and reconnects after a daemon or
host restart.

### C3 — Command gateway (`CL-04`)

The single `RuntimeClient` seam. Two transports, one interface:

- **Direct scoped API** (`CL-23`) — Cloud calls the runtime's scoped endpoint.
  Simplest; correct for a runtime on a private network.
- **Outbound events** — the runtime posts heartbeat and lifecycle events to
  Cloud, so fleet health needs no inbound access at all.

The demo uses direct scoped API for commands and outbound events for health.

**Done when:** a runtime behind an inbound-deny firewall is operated entirely
from the UI, and deleting the Cloud database does not change what the runtime
executes.

### C4 — Projections (`CL-05`)

Jobs, runs, status, timings — explicitly a rebuildable cache, with a
reconstruction path that is a tested procedure rather than an assertion.

### C5 — Idempotency and audit (`CL-11`, `CL-19`)

Idempotency keys on every mutating command; an audit record for every control
action and every refused authorization.

### C6 — Data discipline (`CL-12`, `CL-13`)

Logs, traces and captures never land in Cloud storage; no client business secret
is readable from the control plane. Both are asserted, not asserted-by-document.

### C7 — Baseline control-plane operations (`CL-16`, `CL-18`)

For `v0.4.0`-era Phase B this is deliberately minimal: its own health endpoint,
a backup, and a small hardening pass (no default credentials, TLS, bounded
request size, rate limit on the command gateway). Full `CL-18`/`CL-20` follow
before a paying client.

### C8 — Provisioning hook (`CA-06`–`CA-18`, Phase D seed)

Registration is the thin end of client onboarding. This plan lands only the
registration call and a smoke test; the full one-host-per-client automation is
Phase D.

## 6. Track U — the demo UI

**Requirement: very small surface, demo-quality polish.** The UI is the
deliverable that is seen; the control plane behind it is allowed to be plain.

### U1 — Reuse the existing design language

`castor-app` already carries a polished Tailwind 4 + React 19 shell: sidebar,
topbar, cards, status pills, breadcrumbs, a mocked sign-in (`app/app/layout.tsx`,
`app/components/app-navigation.tsx`, `app/globals.css`). The Otter Cloud UI
copies that shell and its tokens rather than inventing a second design system.
That is most of "looks good" for free.

### U2 — Screens

| Screen | Shows | Real data from |
| --- | --- | --- |
| Sign in | Email → workspace | C1 |
| Fleet | Runtimes, health, version, last heartbeat | C2, `CL-07` |
| Runtime detail | Jobs on that runtime, connection state | C2, C3 |
| Jobs | Job list, schedule, pause state, last outcome | projection, `CL-22` |
| Job detail | Schedule editor, run history | C4, C5 |
| Run detail | Timeline, status, exit code, log tail | C4 |
| Actions | Run now, pause, resume, set schedule | C3, C5 |

Deliberately absent: dashboards, charts for their own sake, settings, user
administration, billing, anything multi-page that does not appear in the demo
script.

### U3 — The demo script

One reproducible path, runnable offline:

1. Fleet shows Castor's runtime, healthy, with a version and a heartbeat.
2. Open the runtime; the three Shopify imports are listed with their schedules.
3. Open one job; pause it from the browser, show the paused state.
4. Run now; watch the run appear and move accepted → running → succeeded.
5. Open the run; show the timeline and the log tail.
6. Show the second organization, and that the same user cannot see Castor's
   runtime.
7. Resume the job.

Every step must work with the network unplugged. The demo runtime is local.

### U4 — Demo data

The three real Castor Shopify jobs, on a seeded local runtime, plus one
deliberately failing run so "diagnose a failure" is part of the demo.

## 7. Sequencing

Roughly eight weeks of one engineer's attention, assuming the runtime items are
built by whoever owns the runtime.

| Week | Track R | Track C / U | Checkpoint |
| --- | --- | --- | --- |
| 1 | `CA-55` recorded; R1 design | Decisions confirmed; repo + CI scaffolding; UI shell from castor-app | Skeleton runs |
| 2 | **R1 `CL-21` lands** | C1 identity + org scoping; U2 fleet screen | Scoped credential in use |
| 3 | R2 schedules: API surface, payload, idempotency | C2 registry + heartbeats; U2 runtime detail | Fleet is live |

Track R is the critical path for the *paying-customer* version. Track U is the
critical path for the *demo*. They interleave so that neither waits on the other
for more than a week.

## 8. Gates

### Demo gate (end of week 8)

- The demo script in §6.3 runs end to end, offline, without author intervention.
- No runtime admin token exists anywhere in Cloud (guardrail 1).
- A duplicated "Run now" produces one run (guardrail 3).
- The second organization cannot see the first (C1).
- Logs render in the UI and are absent from Cloud storage (guardrail 4).
- It looks good: one design system, no unstyled states, empty states and errors
  designed rather than defaulted.

### Paying-customer gate (later; unchanged in substance)

Everything in [cloud-alpha-readiness.md §18](cloud-alpha-readiness.md#L1076)
"Before the first paying client's production schedule", plus the Phase A
sign-off with a **named owner and a date** — still `⟨name⟩`/`⟨date⟩` today
([cloud-alpha-readiness.md:992](cloud-alpha-readiness.md#L992)) — and the
per-workstream sizing `R-23` requires
([:998–1001](cloud-alpha-readiness.md#L998-L1001)).

## 9. Decisions this plan takes

1. **The control plane and UI are TypeScript**, reusing `castor-app`'s
   vinext/React/Tailwind stack and CDK/Cloudflare deployment patterns. Rationale:
   the UI is the hard part to make look good, the stack already exists in the
   workspace, and the control plane only speaks HTTP to runtimes. *Override if*
   you want the control plane to share Go types with the runtime — that is the
   one real alternative.
2. **The control plane lives in a new sibling project**, `otter-cloud/`, not
   inside `otter/` or `castor-app/`. Rationale: it is the multi-tenant product;
   Castor is one of its clients, not its host.
3. **The demo runs locally**, with a deployed variant for remote demos.
4. **`CL-21` ships before any control-plane credential exists**, per guardrail 1.

## 10. Explicitly out of scope

Kubernetes, multi-region, shared multi-tenant execution, autoscaling, billing,
self-service provisioning, workflow canvas, enterprise RBAC, connector
marketplace. All of these are already listed as out of scope for the alpha
([cloud-alpha-readiness.md §16](cloud-alpha-readiness.md#L832)) and nothing in
this plan changes that.
