# Otter v0.2.0 — Dependable execution

Status: release notes. Date: 2026-09-28. Previous release: `v0.1.19`.

`v0.2.0` is a **minor** release. It closes Phase 1 of the
[product roadmap](../product-roadmap.md): accepted work is accounted for, even
after a hard kill. It changes runtime **behavior** and publishes a new document;
it ships **no schema migration** and no manifest, CLI-JSON or HTTP API shape
change. Read the semantics below before upgrading.

## Recovery is complete

`v0.1.19` stopped recovery from losing accepted work; `v0.2.0` closes the
remaining gaps, so interrupted or newly claimed runs can no longer be stranded.

- **Every interrupted run is recovered.** Startup reads *all* `running` rows,
  not the first 50. The old listing limit silently capped recovery at 50 runs,
  so a busy crash left the rest permanently non-terminal. Recovery now pages the
  whole status. (`v0.1.19`; `TestCrashRecoveryHandlesMoreThanOneListingPage`,
  `TestReconcileQueueReenqueuesMoreThanOneListingPage`.)
- **A claimed run that cannot start returns to the queue.** If loading the run
  or marking it `running` fails on a transient database error, the attempt is
  re-enqueued with a 5s backoff instead of sitting as `queued` with no queue row
  until the next restart. A run whose record no longer exists is dropped once,
  at `warn`. (`v0.1.19`; `TestClaimedRunIsRequeuedWhenMarkRunningFails`.)
- **Capacity is not leaked.** A claim that fails to commit releases the worker
  slot it reserved, so a daemon no longer quietly runs fewer workers than
  configured. (`v0.1.19`; `TestClaimCommitFailureReleasesCapacity`.)
- **Finish and retry are one durable decision.** The terminal status, the
  successor attempt and its queue row are written in a single transaction. A
  crash between them can no longer leave a terminal failure whose retry is
  missing, and a `Finish` write that fails after a successful child is recorded
  in a fallback journal and applied on the next start rather than re-running the
  child. (`5481e1c`; `TestFinishCommitFailureLeavesNoPartialOutcome`,
  `TestFallbackJournalIsAppliedOnRestart`.)

## Startup can now refuse

A startup that could not repair interrupted work used to log the error and open
for new work, turning one transient database error into permanently stranded
runs. `otterd` is now **fail-closed**: if crash recovery or queue reconciliation
cannot complete, startup returns an error and the process exits.

- The safe failure is a daemon that stays down and visible, not one that serves
  while accepted work sits stranded. This is the user-visible change: a bad
  database now stops the daemon instead of letting it run degraded.
- The one escape hatch is explicit: `--allow-incomplete-recovery`
  (`OTTER_ALLOW_INCOMPLETE_RECOVERY=true`) starts anyway and logs the error at
  `error` level, for an operator who must bring a daemon up to inspect or repair
  a database it cannot read.
- A failure to persist the repair of *any* interrupted run counts, not only a
  failure of the initial read.

(`ec01900`; `TestStartupFailClosedOnIncompleteRecovery`.)

## Child lifetime is platform-specific

- **Linux: a child cannot outlive an abruptly killed daemon.** The child is
  launched with `Pdeathsig: SIGKILL`, so `kill -9`, an OOM kill or a panic kills
  the direct child before its retry can overlap it. This is the guarantee that
  stops duplicated external effects after an abrupt death.
- **macOS: the exposure is now stated, not implied.** Darwin has no
  parent-death signal. After an abrupt daemon death the in-flight child is
  reparented and keeps running while startup marks the run failed and retries
  it, so non-idempotent work can run twice. Closing this needs a supervisor
  process or a death-watch pipe inside the child; it remains unscheduled.
- The graceful paths — timeout, cancellation and daemon shutdown — are
  unchanged and still signal the whole process group on every platform.

(`2220509`; `TestChildDiesWhenDaemonIsKilled`, Linux only.)

## The runtime contract is published

[runtime-contract.md](../runtime-contract.md) (contract version 1) is the
versioned statement of what the runtime promises and, just as importantly, what
it does **not**. It pins the attempt state machine, what an accepted request
promises, missed cron windows, duplicate webhook delivery, state-write
concurrency, retry effect duplication, and the platform-specific guarantees. It
is backed by the WS4 fault matrix, whose evidence status is stated per scenario.

Two honest non-guarantees worth reading before relying on them:

- **Exactly-once is not promised.** Execution is at-least-once in effect; a
  retry can repeat external effects.
- **A retry's bound release and environment are implemented but not yet
  independently proven.** A retry is recorded with its parent's release and
  environment and is expected to re-use them, but no automated scenario proves
  the retry half yet; it is tracked as `OT-011` in
  [open-work.md](../open-work.md).

(`b5a4001`.)

## Upgrade from `v0.1.19`

- **No schema migration.** No migration shipped between `v0.1.19` and `v0.2.0`,
  so upgrade and downgrade are a binary swap. Keep the usual database backup for
  any operational change, but no data conversion runs.
- **No manifest, CLI-JSON or HTTP API shape change.** The only new flag is
  `--allow-incomplete-recovery` / `OTTER_ALLOW_INCOMPLETE_RECOVERY`.
- **Startup can now fail where it previously warned.** A daemon whose database
  cannot be repaired will not start. That is the intended change; use
  `--allow-incomplete-recovery` only to inspect or repair, not to keep serving.
- **Linux binaries now use `Pdeathsig`.** The behavior change is visible only
  after an abrupt daemon death.

## Verification

`make test`, `make smoke`, `make lint`, `goreleaser check` and
`goreleaser release --snapshot --clean` pass on the tag commit. The `release`
workflow runs the same `test` and `smoke` jobs before GoReleaser publishes, so a
tag cannot publish a binary that fails the loop a user performs.
