# Otter v0.5.3 — Delete a job, from the command line

Status: release notes. Date: 2026-10-08. Previous release: `v0.5.2`.

`v0.5.3` is the client half of job deletion. `v0.5.2` shipped the runtime side —
a job known only from its releases can be deleted, and the agent accepts a delete
command — but nothing in the CLI could ask for one. This release adds the verb, a
confirmation in front of it, and the rule that it names a job rather than a
directory.

Read this first:

- **Deletion is irreversible and the command now asks.** It prints what it will
  destroy, names the job, and waits for `y`/`yes`. Anything else — `n`, blank, end
  of input — aborts with `aborted; nothing was deleted` and exit 1. The default is
  No, so a stray Enter does nothing.
- **A scripted delete needs `--yes`.** Non-interactive input without it is
  refused rather than assumed: the prompt never reads a piped answer as consent,
  and it never hangs waiting for one.
- **The argument is a job name or id, never a directory.** `otter delete .` and
  `otter delete jobs/counter` are refused with a usage error (exit 2), before the
  prompt and before any request. The confirmation can only name something an
  operator recognises, and a path is not that.

## Deleting a job

```sh
otter delete counter                    # the local runtime
otter delete --cloud counter            # a pooled runtime, through Otter Cloud
otter delete --cloud counter --runtime rt-pool-2
```

`--cloud` resolves the credential from `otter login` (or `OTTER_CLOUD_TOKEN`),
finds the job by case-insensitive name or by id, and requires a `deploy`-scoped
token: a `read` token is refused. Deleting a job with a run in flight is refused
with the run named; cancel it first.

The runtime reports what it could not remove, and that report is printed rather
than swallowed. The case that matters: a job known only from its releases has no
tombstone, so releasing the same job id again brings it back.

## What a delete removes

Every run of the job and the logs those runs produced, every captured request and
response payload, the job's stored state, every schedule it owns, its
configuration, and every release including the active one. Source files in the
jobs directory are left in place.

## Limitations

- **A dedicated (non-pooled) runtime's job cannot be deleted from Cloud.** The
  runtime's own delete is admin-only, and Cloud deliberately holds no admin
  credential, so the request is refused rather than half-performed.
- **The note is the only warning you get** that a release-only job can reappear.
  It is carried from the runtime through the control plane to the terminal, which
  cost three hops to get right and is worth knowing about if it ever goes quiet.
