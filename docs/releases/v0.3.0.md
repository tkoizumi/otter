# Otter v0.3.0 — Operable unattended

Status: release notes. Date: 2026-10-02. Previous release: `v0.2.0`.

`v0.3.0` closes the first half of Phase 2. It is a **minor** release: it adds
capabilities and documented semantics and corrects documents. Two facts a reader
must know before upgrading:

- **It ships two schema migrations** (`0011_job_terminology`, `0012_job_schedules`).
  An upgrade therefore runs migrations on first start, and a rollback is a
  **restore**, not a binary swap.
- **The `integration` → `job` rename is public.** The manifest file and every
  manifest field are unchanged, but the names a client or a child process reads
  are not.

## Read this first: the rename is on the wire

| Surface | `v0.2.0` | `v0.3.0` |
| --- | --- | --- |
| HTTP and CLI JSON | `integration_id` | `job_id` |
| Child environment | `OTTER_INTEGRATION_ID`, `OTTER_INTEGRATION_NAME`, `OTTER_INTEGRATION_DIR` | `OTTER_JOB_ID`, `OTTER_JOB_NAME`, `OTTER_JOB_DIR` |
| Daemon configuration | `OTTER_INTEGRATIONS_DIR` | `OTTER_JOBS_DIR` |
| Manifest file and fields | `otter.yaml`, `name`/`entrypoint`/… | **unchanged** |

The embedded Python SDK reads the new names, so a job that uses `otter.Context`
needs no change. A job that reads `os.environ["OTTER_INTEGRATION_ID"]` directly,
or a dashboard that parses `integration_id` out of `otter runs --json`, must be
updated. Migration `0011` renames the affected database columns; the rows are
preserved.

## You can watch an upgrade

The operations guide told an operator to watch for `migration_applied` on
restart, and `database.Migrate` had no logger, so a successful upgrade was
silent — the one moment the schema moves was the one moment nothing was said.

- **One `migration_applied` record per applied migration**, at `info`, in the
  order they were applied, carrying the migration's `version` and `name`
  (`name` is the filename, which is also its description; no new column was
  added).
- **A restart with nothing pending logs nothing**, so "no migration lines" means
  the schema did not move rather than that nobody looked.
- **A failed migration is named before the process exits**: `migration_failed`
  at `error`, with the version and name, and the schema stays at the last
  version that committed. A repaired migration can be shipped and the next start
  continues from there.

## You can operate it unattended

`/health` answered "how many?" and none of "how old?", "which job?", "did it
stop succeeding?", "is the disk filling?". One integer of queue depth cannot tell
a busy queue from one stuck since yesterday, and a job failing since its last
success still showed healthy totals.

For an **authenticated caller only**, `/health` now carries:

- **`queue`** — the age of the oldest run that is claimable *now*
  (`available_at <= now`), the queue depth per job, the count of runs parked by
  retry backoff, and when the soonest of them is due. Retries are reported
  separately from the age on purpose: they wait on a clock, not on capacity.
- **`freshness`** — each job's last success and its age, from one grouped read.
  A job that has never succeeded omits both fields; that absence is the signal.
- **`storage`** — `db_bytes` (`page_count * page_size`, so the WAL is excluded)
  and the data directory's free and total bytes. The guide previously made
  "alert when `otter.db` exceeds about 2 GB" a host-level check, which a remote
  operator cannot perform; now they can.

Each block degrades on its own and is logged when it does. The unauthenticated
liveness body is unchanged, field for field, so a caller without a token learns
nothing new. `otter status` prints the same signals, and `otter jobs --schedule`
renders the daemon's last success instead of listing runs once per job.

## Retention is automatic, and a deploy prunes releases

- **Runs and run logs expire** on their own windows (`--run-retention`,
  `--log-retention`), with `--capture-retention` already covering HTTP payloads.
  Every window is opt-in and defaults to retaining forever, and the tracked
  windows are committed in `otter.deploy.yaml` so a rebuilt host cannot silently
  retain forever. The documented manual-pruning SQL is corrected to filter on
  `runs.created_at`; it was filtering on a column that does not exist.
- **`otter deploy` prunes inactive releases** with the same `--keep` window a
  release uses (default 3, `0` keeps everything), and **every prune path refuses
  to act when the pin set is unreadable**. A queued or retried attempt keeps its
  bound release whatever happens to the release directory.

## The backlog answer is written down

"What happens if a run outlasts its next scheduled run?" runs opposite to
intuition, and it was written nowhere. `operations.md` §"Backlog behavior" now
states all five consequences: every cron occurrence becomes its own run
unconditionally; with `concurrency: 1` they serialize into a catch-up backlog;
**downtime skips while slowness accumulates** (occurrences during downtime are
never replayed — the linked contract section is an explicit non-guarantee);
queued work executes the release bound at *submission*, so a deep backlog can run
older code than what is active; and raising `concurrency` produces genuinely
concurrent executions. No behavior changed.

## A downgrade is refused, and the procedures are drills

- **A database migrated by a newer binary is refused.** Migrations are
  append-only, so a binary that does not embed the database's newest migration
  exits with `migration_failed` naming both versions, before anything reads or
  writes the schema. Before this release, "downgrades are not supported" meant
  "starts, then fails on the first query that touches a renamed column".
  Rolling back remains a restore of the pre-upgrade backup.
- **The operating procedures are executable.** `make drill` runs drills that
  assert their own outcome: `backup-restore` (a hot backup restores onto a
  different, empty data directory and the job runs again), `upgrade` (the
  previous release's schema upgrades observably, and the runtime works after),
  `downgrade-refusal`, `secret-rotation`, `fresh-archive` (a release archive
  installs outside the checkout and runs a job), `deploy-failure`, `unit-caps`,
  `disk-pressure` and `liveness`. Each documents a `DRILL_SABOTAGE` mode that
  removes the behavior under test, so a green run is demonstrably falsifiable.
- **A retry keeps its bound release and environment.** Activating a newer
  release, changing the interpreter, or changing the retry policy while a retry
  is pending cannot move that retry onto different code, a different
  environment, or a different policy; a pending backlog also keeps its digest
  through a release prune. This is now a **guarantee** in
  [runtime-contract.md](../runtime-contract.md#5-retries-and-external-effects),
  pinned by `TestRetryExecutesTheParentsReleaseSnapshot`,
  `TestRetryResolvesTheParentsManagedEnvironment`,
  `TestPendingBacklogKeepsItsDigestThroughAReleasePrune` and
  `TestRecoveryPlansRetriesFromTheBoundRelease`.
- **The trust-boundary claims are asserted**, not restated: the data directory
  is created owner-only, a non-loopback bind without a token is refused, the
  unauthenticated `/health` body carries only status, version and uptime, a
  per-run token cannot read another job's run, logs or state, and a webhook
  token authorises only its own job's hook and is never recorded on the run.

## Also in this release

- **Schedules are runtime state.** `otter schedule set|clear|show` (and
  `PUT`/`DELETE /v1/jobs/{id}/schedule`) change a job's cadence without editing
  the manifest or restarting; a cleared schedule is deliberate and does not fall
  back to the manifest (migration `0012`).
- **A deploy can bind the API to a private address**, not only loopback.
- **Managed Python is harder to misconfigure**: a lock the configured package
  index cannot satisfy is refused, preparation has an explicit route with an
  egress preflight, and the generated unit defaults `MemoryHigh` to off so
  `MemoryMax` is what kills a runaway.

## Upgrade from `v0.2.0`

1. **Back up first** — the complete backup, not just the database
   ([Backups](../operations.md#backups)). An upgrade runs migrations on first
   start.
2. Stop the daemon, replace both binaries, start it, and **watch the journal for
   one `migration_applied` per migration** (`0011`, `0012`).
3. `otter status`, `otter jobs`, `otter runs --all --limit 10`.
4. **Release every job once.** The release layout is versioned and the new
   implementation deliberately does not reuse a snapshot laid out by an older
   one, so a job must be re-released before runs resume executing current code.
5. Update anything that reads `integration_id` or `OTTER_INTEGRATION_*`
   (see the table above).
6. **To roll back, restore the backup.** An older binary against this database
   is refused, and a database restored from the pre-upgrade backup is the only
   supported way back.
