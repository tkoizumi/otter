# Otter v0.4.0 — The interface freeze

Status: release notes. Date: 2026-10-03. Previous release: `v0.3.0`.

`v0.4.0` completes the runtime half of Track R: a scoped control credential,
first-class dynamic schedules, a reachable-but-scoped remote API, pinned job
configuration, and the published compatibility policy that freezes the manifest
schema, the Python SDK, CLI JSON and the HTTP API.

Read this first:

- **It ships three schema migrations** (`0013_api_tokens`,
  `0014_dynamic_schedules`, `0015_job_configs`). An upgrade runs them on first
  start, and a rollback is a **restore**, not a binary swap: a newer schema is
  refused by an older binary by design.
- **Two shapes break.** A cron expression now means UTC rather than the host's
  local time, and every list response is an object rather than a bare array.
  Both changed deliberately, before the compatibility promise takes effect, and
  both are recorded in [compatibility.md](../compatibility.md).
- **The runtime contract is version 2** and reached from
  `GET /v1/version` or `otter --json version`.

## What breaks, and what does not

| Surface | Before | `v0.4.0` |
| --- | --- | --- |
| `trigger.cron` time zone | the host's local time | **UTC**; use a schedule's `timezone` for a local wall-clock meaning |
| `GET /v1/jobs`, `/v1/runs`, `/v1/runs/{id}/logs`, `/v1/tokens`, capture requests | a bare array, or an object with no version | `{"schema_version": 1, "jobs": [...]}` and the matching key per endpoint |
| `otter jobs --json`, `otter runs --json` | a bare array | the same versioned envelope as the HTTP API |
| `PUT`/`DELETE /v1/jobs/{id}/schedule`, `otter schedule set\|clear` | the supported cadence surface | **deprecated**; still work, removed in the next major |
| A manifest-declared `trigger.cron` | the API could overwrite it | it is `manifest`-owned; `PATCH`/`DELETE`/legacy `PUT` refuse it with `409` |

A job that reads `ctx.trigger`, `ctx.state` or its environment needs no change.
A script that parses a list response does: add `.jobs` / `.runs` / `.logs` /
`.tokens` / `.requests` / `.schedules`. The old line-oriented CLI output is
unchanged.

## Scoped control credential (`CL-21`)

Named API tokens with `read` and `control` scopes, minted by
`otter token create`, stored as a SHA-256, revocable with immediate effect (the
row is read on every request). Full authority stays the static `OTTER_API_TOKEN`;
a named admin token is deliberately not offered. The route-by-route boundary is
in [api-reference.md](../api-reference.md#scoped-api-tokens).

## Dynamic schedules (`CL-22`)

A schedule is now a first-class, id-keyed runtime object, not one cadence per
job buried in a manifest.

- `GET`/`POST /v1/jobs/{id}/schedules`, `GET`/`PATCH`/`DELETE
  /v1/schedules/{id}`, and `pause`/`resume`; `otter schedule
  list|add|update|remove|pause|resume`.
- A per-occurrence `payload` becomes `ctx.trigger.body`, so "this job, for
  dataset 42" is expressible without a release.
- `Idempotency-Key` on create: a retry returns the existing schedule.
- Exactly one run per occurrence, across restarts and duplicate wake-ups: the
  occurrence ledger (`schedule_fires`) is written in the same transaction as the
  run.
- A manifest's `trigger.cron` reconciles as a `manifest`-owned row that the API
  cannot change; an API-created schedule is never touched by a reload.

**Known limit:** the missed-occurrence policy accepts only `skip`.
`coalesce` and `catch_up` are reserved names and are refused with `400` rather
than accepted and ignored (`OT-007`).

## Reachable, scoped remote surface (`CL-23`)

`otter deploy` accepts a wildcard or public `--listen` behind an explicit
`--allow-remote-bind` and prints a warning; a private bind warns without the
opt-in. `assert-host-permissions.sh` asserts the **configured** posture and
requires `OTTER_API_TOKEN` for any non-loopback API. TLS remains a documented
reverse-proxy pattern ([security.md](../security.md#remote-access-tls-and-reverse-proxies));
the daemon still serves plain HTTP behind it.

## Job configuration

A job's configuration is the layer between the release and the run: a store
name, a dataset id, a backfill date. It is versioned and immutable, and every
run pins the version it resolved at submission, so a queued, retrying or
backlogged attempt keeps its values.

- `GET`/`PUT /v1/jobs/{id}/config`; admin-only to write in `v0.4.0`.
- The child reads `ctx.config` (a dict; `{}` when unconfigured), passed as
  `OTTER_CONFIG`.
- **Not** a secret store: values are returned to any scoped reader and are not
  projected into named environment variables in this release.

## Interface freeze (`R4`)

[compatibility.md](../compatibility.md) publishes what makes a change breaking
for each frozen interface, how a deprecation is retired (one minor release
minimum, removal only in a major), and the current deprecation table.
`GET /v1/version` and `otter --json version` report `schema_version`,
`contract_version`, the manifest schema, the SDK version and the supported
platforms in one document. Contract tests pin the version document, the platform
list and the frozen JSON keys of every machine document.

## Also in this release

- `OT-010`: release retention and a submission binding a release now serialize
  on the database write lock, so a prune cannot strand a queued run.
- `OT-024`: the CloudWatch metric contract is one file,
  `monitoring-contract.json`, asserted on both the runtime and the platform
  side.
- `OT-029`: a retired job whose source is still in the repository no longer
  fails a full deploy; the release step skips and reports the suppressed path.
- The runtime contract gains §7 "Honest limits": uncoordinated concurrent
  updates, retry effect duplication, no downgrade, plain-HTTP transport, and
  configuration not being a secret store.
