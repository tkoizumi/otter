# Otter v0.5.0 — Self-serve deploys to Otter Cloud

Status: release notes. Date: 2026-10-07. Previous release: `v0.4.0`.

`v0.5.0` makes a job deployable by the person who wrote it: `otter login` against
Otter Cloud, `otter deploy --cloud --job <name>` to package and promote one job
to a runtime the organization owns, and a pooled tenant that runs it. The runtime
half of the pipeline already existed; this release is the client half and the
hosting that makes it real.

Read this first:

- **The tenant container changed shape.** A pooled tenant is now **one**
  container running two processes: `otterd` as uid 10001 and the agent as uid
  10002, over loopback. The separate sidecar container is gone, and an existing
  tenant must be re-provisioned rather than upgraded in place.
- **`otter login` needs a token** minted in Otter Cloud; there is no browser or
  device flow. It is read from `--token`, `OTTER_CLOUD_TOKEN`, or a terminal
  prompt, and stored per machine under `~/.otter/cloud.json` (0600).
- **Assigning a runtime is an API call.** `POST /api/runtimes` creates the
  organization's assignment and returns the per-runtime bootstrap secret once;
  it is session-authenticated and has no dashboard page yet.

## Deploying a job

```sh
otter login --cloud https://app.runotter.dev --token <token>
cd my-workspace
otter deploy --cloud --job <name>
```

`deploy --cloud` packages one job with the same release machinery `otter
release` uses, so the digest it promotes is the canonical release identity, and
asks the control plane to move the assigned runtime onto it. `--dry-run` and
`--runtime` are honoured; `otter login --status` reports the stored identity
without deploying.

A deploy installs and activates a release. It does not run anything: the run is
a separate act, and on a pooled runtime it is triggered from the job's page in
Otter Cloud.

## One container per tenant, two uids

The agent must reach `otterd` over loopback, and gVisor cannot give it that
across containers: it does not honour `--network=container:<other>` (a joining
container comes up with only `lo`), and a container's listener is not reachable
across a gVisor bridge either. So both processes live in **one** container and
share a network namespace by construction. `otterd` is loopback-only and needs
no API token, and nothing is exposed on any bridge.

The isolation the separate sidecar existed for is kept by uid separation, and it
is why the container starts as root:

| Process | uid | Access |
| --- | --- | --- |
| `otterd` | 10001 | owns the tenant volume, mode 0700 |
| agent | 10002 | its own tmpfs, **cannot read or write the tenant volume** |

Root is needed only to drop to those two uids; the container is granted exactly
`SETUID`, `SETGID` and `CHOWN`, and runs with `no-new-privileges`. After the drop
no process holds a capability. The agent's Cloud credential is stripped from
`otterd`'s environment, so the tenant process cannot read it.

## What the agent does differently

- **Released jobs are discovered.** A runtime whose workspace is empty still
  resolves the job a release was installed for, by name and by id, so a deploy
  to a pooled tenant is runnable without any source in `/workspace`.
- **Applying is idempotent.** A control plane publishes desired state and keeps
  returning the same generation; the agent now compares the content it observes
  against what is desired and does nothing when they match. Before this, a stable
  desired state re-downloaded and re-activated the same release every few
  seconds and leaked a staging directory on each pass.
- **Polling is paced**, and its decisions are logged to stderr — which in a
  container is the container log. The agent used to be silent, which made a
  stalled deploy indistinguishable from a working one.

## Fixes worth naming

- Installing a release that was already in the store left its staging directory
  behind; cleanup is now unconditional.
- The pool resolver now binds and checks **every** tenant gateway. It previously
  reloaded a unit that declares no `ExecReload`, so a newly added tenant's
  gateway was never bound, and the health check probed only the first gateway —
  reporting healthy while the new tenant's agent could not resolve anything.
- The agent data directory is `chmod`ed before it is `chown`ed; the other order
  needs `CAP_FOWNER`, which this container deliberately does not have.

## Installing

Homebrew (macOS):

```sh
brew install tkoizumi/tap/otter
```

The cask installs the two prebuilt binaries, `otter` and `otterd`; no Go
toolchain is needed.
