# Otter v0.5.4 — Per-job desired state, and a delete that sticks

Status: release notes. Date: 2026-10-08. Previous release: `v0.5.3`.

`v0.5.3` added `otter delete --cloud` and it did not work. The delete removed the
release on the runtime, the control plane still desired it, and the agent
converged the runtime back onto it within four seconds — so the job reappeared,
while the command reported success and a note claiming every release was removed.
This release fixes the cause: a runtime's desired state is now a set of jobs, one
entry per job, instead of a single release.

Read this first:

- **Deleting a job now removes it from Cloud's desired state**, which is what
  stops the runtime being reconciled back onto it. Until this release, deletion
  and convergence were fighting and convergence always won, because it retries.
- **One job's deploy no longer disturbs another's.** The desired state was a
  single digest per runtime, so deploying job B overwrote what job A was relying
  on. Each job is now addressed by its stable job id.
- **Cloud only reports a delete as done once the runtime confirms it.** A
  removal that has not been confirmed is `pending`, not `deleted`.
- **The agent protocol gained a capability** — see below. It is additive and
  gated, so nothing breaks during a rollout.

## What changed

The desired-state answer from the control plane is now a snapshot:

```jsonc
{ "runtime_id": "…", "generation": 12, "snapshot": true,
  "jobs": [ { "job": "<durable job id>", "digest": "sha256:…", "url": "…" } ] }
```

The agent converges the **set**: it installs and activates what the snapshot
names, and removes managed jobs the snapshot has dropped. Removals are not gated,
so deleting one job never pauses its siblings. It only ever removes jobs the
*runtime* reports as managed, so a job whose source lives in the workspace is out
of reach by construction rather than by a rule someone has to remember.

The runtime-level generation fence is unchanged. Jobs are addressed by their
stable id.

### The capability: `desired.snapshot.v1`

Cloud and agents deploy independently — Cloud on a push, an agent only when a
tenant image is rebuilt — so the shape is **dual-served**, chosen by an explicit
capability:

- the agent declares `desired.snapshot.v1` and reports the releases it holds;
- Cloud serves the per-job shape only when the agent declares the capability
  *and* the runtime says it can identify and remove managed jobs;
- otherwise the previous single-release shape is served, unchanged, and an agent
  that receives no `snapshot` marker removes nothing.

Adoption of per-job state is **seeded from what the agent reports it already
runs**, never from an empty table — an empty snapshot means "delete every managed
job", so seeding from nothing would have ordered the release store emptied.

## Three ways this could have failed silently

Recorded because each was caught late and each would have looked like success:

- **A missing `snapshot: true` marker.** The agent keys on it, so a per-job answer
  without it decodes as the legacy shape: nothing deployed, nothing removed.
- **Confirmed by silence.** An empty release list in a report could wipe the
  stored observation and read as confirmation that a removal had happened. The
  stored set is now only replaced when the field was present, it is nullable so
  "never reported" is not "reported empty", and a removal requires an observed set.
- **A stale single-release projection.** After a snapshot delete, the legacy
  projection still named the deleted digest, so one poll from a not-yet-upgraded
  agent could re-install it. It is cleared before the delete.

## Installing

```sh
brew upgrade otter
```

Linux packages are on the release page, per architecture. Upgrading the client
before the runtime matters: a runtime that becomes snapshot-capable expects the
deploy to name a job id, which older clients do not send.

## Compatibility

This is the first agent-protocol change since the compatibility policy in
`v0.4.0`. It is additive: a new optional capability, dual-served, with old agents
receiving exactly today's shape and new agents falling back safely. No manifest,
SDK, CLI-JSON or HTTP shape that the policy froze is changed.
