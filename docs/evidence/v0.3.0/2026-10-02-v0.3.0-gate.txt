--- F1 (release blocker): `otter start --detach` silently drops forwarded daemon flags ----

Reproduction (raw output in 2026-10-02-v0.3.0-finding-start-detach-flag-forwarding.txt):

    $ otter start --detach --listen 127.0.0.1:7816 --api-token s3cret --workers 2 --log-format pretty
    $ grep api_listening .otter/serve/serve.log
    {"auth_required":false,"event":"api_listening","level":"info","listen":"127.0.0.1:7816",...}
    $ grep daemon_started .otter/serve/serve.log
    {...,"event":"daemon_started",...,"workers":8}
    $ curl -s http://127.0.0.1:7816/health | python3 -c '...sorted keys...'
    ['freshness', 'jobs', 'queue', 'queue_depth', 'status', 'storage', 'uptime_seconds', 'version']

The token is not applied (`auth_required:false`), `--workers 2` is not applied
(`workers:8`), `--log-format pretty` is not applied (the log stays JSON), and an
unauthenticated caller therefore receives the full operational payload. The same flag in
the foreground path *is* applied:

    $ otter start --listen 127.0.0.1:7843 --api-token s3cret &   # no --detach
    {"auth_required":true,"event":"api_listening","listen":"127.0.0.1:7843",...}
    $ curl -s http://127.0.0.1:7843/health | ... keys ...
    ['status', 'uptime_seconds', 'version']

Cause (observed, then read): the foreground path builds the daemon argv with
`daemonArgs(...)`, which forwards every flag the operator typed; `startDetached` rebuilds
the child argv from `--jobs`, `--data`, `--listen` plus trailing passthrough only
(`internal/cli/start.go:426-430`), dropping every other parsed flag. The bug also exists in
`v0.2.0` (`git show v0.2.0:internal/cli/start.go`, same construction), so it is not a
v0.3.0 regression — but v0.3.0 ships it.

Classification: **product defect + documentation defect.** The product silently ignores
flags it accepts; `otter start --help` (a published instruction, and `--help` is in scope
for this gate) states:

    The daemon's own flags are accepted and forwarded, so --workers,
    --log-format, --api-token and the rest work here too.

Security relevance: an operator who starts a loopback runtime with `--api-token` believes
the control-plane API requires a token. It does not. Nothing prints a warning. (A loopback
bind is the documented default, and `OTTER_API_TOKEN` in the environment or in
`otter.env`/`otter.daemon.env`, or `otterd --api-token`, do work, so a workaround exists —
but the published flag does not.)

This is why section 4's `/health` claim is marked disagree: reached through the published
`otter start` path, an unauthenticated caller gets everything.
