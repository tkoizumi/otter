--- schedules paused, and the pause survives a daemon restart ---
The jobs declare cron "*/5 * * * *", so they were paused immediately after the deploy:
the project has no credentials, so every run would fail (and notify, once a channel is set).

shopify_customer_to_salesforce_contact    */5 * * * *      paused      -   no runs yet
shopify-product-to-salesforce-product     */5 * * * *      paused      -   no runs yet

Both jobs are still paused after the restart, with MainPID changed, so the pause is
persisted state and not a process-lifetime flag.

--- verdict ---
Proves: an empty VM converged to a running otterd (v0.3.0-rc1) with the service account
nologin, data dir 0700, both env files 0600 root-owned, the unit enabled and active with
NRestarts 0, the API bound to loopback only, and the P0-04 caps live as resolved values
(MemoryMax 711147520 = 75%, MemoryHigh 568918016 = 60%, CPUQuota 200%, TasksMax 512)
with OOMPolicy=continue and the sandbox directives present.

Also proves, on real arm64 hardware: managed Python prepared CPython 3.13.1 for both
jobs. That is the exact failure docs/managed-python.md warns about ("not every patch
version is downloadable everywhere"); it did not occur, so the t3.micro/x86 fallback
the preflight documents is not needed for this pin.

Does NOT prove: P0-07 as a task. Its evidence bar is the port scan plus a passing
permission assertion test, and the provisioning script that must reproduce this from an
empty VM is still being written. It also does not prove anything about a Castor job:
otter_examples is a stand-in, and both its schedules are paused.
