=== verdict ===
What this proves:
  * The generated unit emits MemorySwapMax=0, the cgroup reads memory.swap.max=0, and while
    the runaway holds 800+ MiB the cgroup's memory.swap.current stays 0 even though a 512 MiB
    swap device is active. The bound is real and load-bearing: memory.swap.max is asserted
    against the unit exactly as memory.max is (mutation red below).
  * With MemoryHigh off, the hard cap binds and the runaway is OOM-killed in well under a
    second: hard-cap (swap 0) and swap-size (64M) both PASS with oom_kill=1, no survivor,
    MainPID unchanged, NRestarts 0 and /health answering.
  * The survivor check is no longer vacuous: it reads the cgroup's process list, and it
    catches a real runaway (deployed-style: survivor pid 182, comm=python3, rss 838176 kB,
    cmdline "python3 -m otter._launcher main.py").

What this does NOT prove, and the reason the deployed claim is still false:
  * With MemoryHigh ON at the deployed 60% (here 20%/25%, the same ratio), MemorySwapMax=0
    does not make memory.max bind in any useful time. memory.high throttles the allocator
    just above the soft cap; with no swap the kernel cannot reclaim the anonymous pages, so
    the process is pinned below memory.max and creeps. Over 900s:
        memory.events:  high 177297  max 0  oom 0  oom_kill 0
        memory.current: 842,346,496 B (803 MiB) at 20s -> 871,403,520 B (831 MiB) at 590s
        memory.high:    824,872,960 B (787 MiB)
        memory.max:     1,031,090,176 B (983 MiB)
        memory.swap.max / memory.swap.current: 0 / 0
    and the growth was decelerating (roughly 1.3 MiB per 20s at the start, ~0.03 MiB/s at
    the end), i.e. it was settling just above memory.high rather than ever reaching the hard
    cap. The only thing that ended the run was the job's own manifest timeout:
        otterd: "event":"run_timeout","timeout":"10m0s"
        otterd: "event":"run_kill","grace":"5s","pid":198
        otterd: "event":"run_finished",..."status":"timed_out",...duration_ms":606760
    P0-04's "killed" clause therefore still does not hold as deployed: MemorySwapMax=0 fixes
    the swap exhaustion and the daemon/host starvation, but MemoryHigh=60% converts the OOM
    kill into a throttle-pin that outlives the job's own timeout.
  * Whether the host kernel behaves identically is not proven here; the container kernel is
    5.10.76-linuxkit. HW-3 (the host command list in the report) is what closes that.
