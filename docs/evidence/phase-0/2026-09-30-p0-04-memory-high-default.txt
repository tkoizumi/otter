--- the change this record covers ---
DefaultMemoryHigh is CapOff ("off"), so a plain `otter deploy` emits no MemoryHigh=
directive and memory.max is the constraint that kills a runaway. The --memory-high flag,
its validation and its docs are unchanged; only the default moved. Rationale, measured
below and in 2026-09-30-p0-04-unit-caps-swap.txt: a soft cap throttles and reclaims
instead of killing, and with MemorySwapMax=0 there is nowhere to reclaim anonymous pages
to, so a hold-everything job parks just above memory.high and creeps toward memory.max.
That turns a one-second OOM kill into a multi-minute pin (measured: 803 -> 831 MiB below
a 983 MiB hard cap with oom_kill 0 for 600s), which on a --workers=1 host occupies the
only worker for the whole timeout. systemd's own default is no soft limit, so "off" is
also the least surprising value.

The deployed-style case exists to protect exactly that constant: it passes no -memory-high
at all (the drill's "default" sentinel), so the generator falls back to
deploy.DefaultMemoryHigh and the rendered unit is what a plain deploy writes. It asserts
the unit carries no MemoryHigh directive and that memory.high reads max. Setting
DefaultMemoryHigh back to 60% turns it red before anything runs (mutation 1 below).
