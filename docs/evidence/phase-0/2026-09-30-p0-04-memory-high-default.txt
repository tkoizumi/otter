--- the change this record covers ---
DefaultMemoryHigh is now CapOff ("off"), so a plain `otter deploy` emits no MemoryHigh=
directive and memory.max is the constraint that kills a runaway. The --memory-high flag,
its validation and its docs are unchanged; only the default moved. Rationale, measured
below and in 2026-09-30-p0-04-unit-caps-swap.txt: a soft cap throttles and reclaims
instead of killing, and with MemorySwapMax=0 there is nowhere to reclaim anonymous pages
to, so a hold-everything job parks just above memory.high and creeps toward memory.max.
That turns a one-second OOM kill into a multi-minute pin (measured: 803 -> 831 MiB below
a 983 MiB hard cap with oom_kill 0 for 600s, ended only by the job's own manifest
timeout), which on a --workers=1 host occupies the only worker for the whole timeout.
systemd's own default is no soft limit, so "off" is also the least surprising value.

The drill was reworked to match: the deployed-style case is now memory-high=off /
memory-swap-max=0 and must kill (it does), and a new soft-cap case exercises the real
feature and asserts its honest consequence rather than failing.
