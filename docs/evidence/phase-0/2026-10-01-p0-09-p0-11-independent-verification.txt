Stack mutation (otter-platform, npx jest):
  remove `cfnAlarm.evaluationWindow = { wallClockWindow: {} }`
      RED: "uses a wall-clock evaluation window, so five periods mean five minutes"
  TreatMissingData.BREACHING -> MISSING
      RED: "creates one alarm per check, and treats missing data as breaching"

THE CRUX, re-derived on the REAL metric, current host. Two verification alarms on
Otter/Heartbeat Host=castor-runtime, identical settings except the window, no
actions; the host's heartbeat timer was stopped (the daemon left running). Latency
is from CloudWatch's own StateUpdate history, from the silence at 02:59:49Z:

  zz-v-walled   (WallClockWindow)  OK->ALARM 23:05:31.383 EDT   342s = 5m42s
  zz-v-sliding  (default)          OK->ALARM 23:10:26.996 EDT   637s = 10m37s
  CastorRuntime-liveness (prod, actions muted) OK->ALARM 23:05:08.699 319s = 5m19s

So the wall-clock window is what makes 60s x 5 mean about five minutes, and the
default sliding window takes nearly twice as long. The production run of the same
drill measured 11m10s and 5m34s (HW-4b, already on this host); this round measures
both arms against the same silence, which the earlier runs did not.

TOLERANCE (the design claim: five periods tolerate one missed minute). A
wall-clock alarm with the production settings was published to for 6 minutes until
OK, one minute was skipped, then publishing resumed for 5 minutes. Sampled
every 20-60s: OK at every sample. RESULT: tolerated. A single missed period does
not alarm.

ABSENT HOST: the same window stopped the heartbeat timer while otterd stayed up;
the alarm fired. A host that can send nothing looks the same as a host that is
gone, which is the switch's premise.

  Note, measured: an alarm created with NO datapoints and treatMissingData=breaching
  goes to ALARM after ~5 minutes of silence (seen in the synthetic ramp:
  INSUFFICIENT_DATA -> ALARM at 03:00:06, then -> OK at 03:01:07 as data arrived).
  That is why a rebuilt host with no checks "looks dead about five minutes after the
  second cdk deploy"; the documented rebuild order (install the checks first) avoids
  it, and the installer header says so.

  Residual: this round muted the alarms' actions, so no new SNS email was observed.
  The alarm->action wiring is unchanged and was owner-confirmed earlier; it was not
  re-derived end to end here.

=== D1 (material) -- the retention deliverable is not in force on the live host ===

The live daemon logs, on every start:

  {"event":"retention_configured","log_retention":"0s","run_retention":"0s"}

and `capture_configured` at its 168h default (no environment variable exists).
The deployed daemon env file contains OTTER_WORKERS and nothing else; there is no
retention key, no unit drop-in and no `retention:` key in `otter.deploy.yaml`.

The ledger's HW-6 row says the live runtime "was left configured
OTTER_RUN_RETENTION=2160h / OTTER_LOG_RETENTION=720h" -- true of the host that
produced HW-6a, 44.213.227.52, which was destroyed the same day. Nothing re-applies
it on a rebuild: the retention windows are enabled only by editing an env file by
hand, and the rebuild procedure in phase-0-resume-here.md does not mention it.

Consequence: CA-33's "define retention ... before enabling unattended jobs" is not
met on the host that would run Castor's job, and a rebuild silently reverts it.


=== D2 -- the suites are green with the behaviour the alarms depend on deleted ===

Spot-checked by this session (not only reported), because it goes to the heart of
the house bar ("a green test that would pass with the behaviour removed is not
evidence"). Every mutation below was run against a copy; the suite stayed green.

  test-otter-metric.sh (29/29 green) with the publisher UNSIGNED:
      delete `--aws-sigv4`, `--user "$ak:$sk"` and the session-token header from
      otter-metric.sh:186-188 -> 29 cases pass. The stand-in accepts any request
      and records no headers, so the SigV4 signature -- the thing that makes the
      metric land -- is asserted nowhere. Real CloudWatch would 403.

  test-disk-check.sh (18/18 green) AND the disk-pressure drill (green) with the
      DISK CHECK PUBLISHING THE WRONG METRIC:
      disk-check.sh:233 `DiskCheck=1 DiskFreeMB="$free_mb"` -> `AnythingIsFine=1`
      -> 18 cases pass and the drill passes. The P0-11 alarm is on Otter/DiskCheck;
      the check could publish nothing the alarm reads and every test still passes.

Additional holes confirmed by an independent sub-audit (report kept; substantive):

  * `assert_log` is an unanchored substring match: Namespace Otter->OtterMetricsX,
    StorageResolution 60->600, dimension Host->HostName, the default host value,
    the metric name and the values can all be *extended* and stay green.
  * The stand-in conflates the CloudWatch endpoint and IMDS (one host:port); the
    publish can be pointed at IMDS and the suite stays green.
  * OTTER_METRIC_REGION is only proven to skip the IMDS lookup; hardcoding the
    signing region elsewhere stays green.
  * The IMDSv2 stand-in checks token *presence*, not value; a bogus token passes.
  * The disk suite's `df` tap ignores its arguments: measuring `/` instead of the
    data filesystem stays green.
  * `heartbeat.sh` is executed by no *suite* (only the committed liveness drill
    runs it). Neutering its publish to a no-op left 165 cases across the five
    test suites green -- but the drill DOES catch it: with `heartbeat.sh:42`
    replaced by `:`, `sh scripts/drill/liveness.sh` exits 1 with "the check did
    not publish for a healthy runtime". The real gap is narrower than "untested":
    a reader of `make test` sees green, and the drills are not in CI either. This
    was checked after the sub-audit reported the stronger claim; the stronger
    claim is wrong.
  * The shell suites are not wired into `make test` or CI; they are manual-only.
  * OT-022 (author-reported) is CONFIRMED: the installer's convergence probe runs
    `[ -f /etc/otter/*.env ]` as the login user against a 0750 root:root directory,
    so it reports both env files missing on every run and the "already converged"
    branch is unreachable. The stack sets `PermitRootLogin no`, so the root login
    that would make it pass is impossible on any host it builds. The suite cannot
    see it because its fixture intercepts the whole probe.

None of this makes the production code wrong -- the publisher and the checks are
correct as deployed, and the real API path was re-derived below. It means the
suites do not prove what the ledger's "verified by mutation" language implies, and
a regression in the signature, the region or the metric name would ship green.
