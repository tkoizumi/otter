Verdict
------------------------------------------------------------------------------

What this proves:
  * a release that fails after the candidate snapshot is staged does not become
    active; `otter release` refuses it at preparation and the active-release
    link still names the previous digest;
  * the previous release keeps serving: the unit is the same process (MainPID
    unchanged), the unit is active, /health answers, and a NEW run submitted
    after the failure succeeds, is bound to the previous release and
    environment digests, and really executes the previous snapshot (the job
    appends its run id into the release snapshot's working directory);
  * the assertion is falsifiable in both directions: activating the unprepared
    candidate turns it red on the active-release check, and stopping the unit
    turns it red on the serving check.

What this does NOT prove:
  * anything about a real host. The target is a privileged container on the same
    machine, not the Castor VM and not a VM at all.
  * binary rollback. Both deploys carry the same compiled binaries; only the job
    release changes.
  * real Python packaging. The deploy vendors scripts/drill/deploy-failure-uv.sh
    as uv, so no interpreter is downloaded and no dependency is resolved; the
    injected failure is a preparation failure of the shape a real one has.
  * failure during `systemctl restart` itself. Activation is the last step of a
    release and the unit is swapped after it; this drill fails the release,
    which is the boundary the two code comments make the claim about.

The verifier's mutation check is the two DRILL_SABOTAGE transcripts above: each
one breaks exactly one invariant and the drill goes red on the matching
assertion, so neither half of "active and serving" can pass vacuously.
