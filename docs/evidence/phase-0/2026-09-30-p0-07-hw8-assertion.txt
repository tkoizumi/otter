--- what this run establishes, and why each part is load-bearing ---
workspace.json: `--workspace-dir` alone now suffices. The script reads the record the
deployer actually writes (unit, name, listen) and derives <workspace>/.otter/data, where
the earlier revision looked for service_name/data_dir and could not start at all.

The sandbox directives are read back from the LOADED unit (systemctl show), not from the
unit file, so a directive present on disk but absent from what systemd runs fails.

Credential files are asserted root-owned 0600 inside a 0700 root directory -- the posture
an independent verifier confirmed in P0-12, and the one that stops a compromised job from
rewriting the credentials it runs under. The earlier revision demanded service-account
ownership, which is the weaker posture and is not what otter deploy does.

otter.db at 644 is reported as ok with an explicit note, not failed: the 0700 data
directory contains it and the documented bar is the directory. A tighter umask would make
it 0600, and the note says so.

Swap (2047 MiB) and the provisioning report are both present because the stack fix works:
the report did not exist on the first host, which is what started that investigation.

--- verdict ---
Both halves of P0-07 evidence bar are met on the real host: an external scan finds only
22/tcp, and the permission assertion exits 0 having read the loaded unit, the real
workspace record, the real file modes and the real listener set.

This does not by itself close P0-07: the scripts are on a branch that is still being
verified (round 2, on whether the fixture suite is now genuinely falsifiable), and the
provisioning script itself refuses an already-provisioned host by design, so it is the
assertion half -- not provision.sh -- that this host can evidence.
