# v0.3.0 release plan

Status: proposed. Date: 2026-09-28. Starting point: `v0.2.0` (`499800e`).

This plan turns the `v0.3.0` gate in [product-roadmap.md](product-roadmap.md) into
a sequence of concrete workstreams. It is a work order, not a commitment to dates.
Each workstream states what it carries, what proves it, and what it deliberately
leaves out.

Unlike `v0.1.19`/`v0.2.0`, this release fixes almost nothing that loses accepted
work. The Phase 1 gate closed: work is accounted for across a hard kill. What is
missing is the *operator's* half — the runtime is dependable but it is not yet
diagnosable, bounded, upgradeable, or restorable by someone who did not build it.
That is the whole content of this release.

## Where `v0.2.0` stands

`v0.2.0` closed Phase 1 and published its evidence: complete recovery, the atomic
finish/retry decision, fail-closed startup, `Pdeathsig` on Linux with the macOS
exposure stated, and contract version 1 in
[runtime-contract.md](runtime-contract.md) backed by the WS4 fault matrix.

A large part of what `v0.3.0` needs already exists and is **not** being rebuilt:

- **Explain a run** is largely shipped. The run timeline (`otter trace`,
  `internal/timeline`), HTTP capture (`otter requests`, `otter request`,
  `internal/inspection`), and the capture-state distinction between "nothing was
  recorded" and "nothing was requested" all exist and are tested. This plan does
  not re-open them.
- **Capture retention** already works and is the template for this release:
  `Daemon.runCaptureRetention` (`internal/daemon/inspection_api.go:201`) expires
  payloads in bounded batches on a ticker, configured by `--capture-retention`
  (`internal/config/daemon.go:58`), default 7 days.
- **Operational surface**: `pause`/`resume`, `reload`, identity migration, secret
  reload, and the SSH `deploy` path are implemented and tested.
- **Documents**: `architecture.md`, `operations.md`, `security.md`, `deploy.md`,
  `api-reference.md`, and `manifest-reference.md` are substantial.

What is missing, in one sentence per gap:

- Run logs grow without bound and the only remedy is hand-written SQL that does
  not run (`OT-001`, `OT-006`).
- A deploy never prunes releases, so every snapshot ever staged stays on disk
  (`OT-003`).
- `/health` reports counts but no age, no per-job depth, no freshness and
  no storage (`OT-004`).
- Migrations are silent, while the ops guide tells an operator to watch a log
  line that is never emitted (`OT-005`).
- The most counter-intuitive runtime behavior — the backlog — is documented
  nowhere (`OT-008`).
- A retry's bound release and environment are implemented but never proven
  (`OT-011`).
- No operating drill — backup/restore, upgrade, secret rotation — has ever been
  scripted or run.

## The decision rule

`v0.3.0` is a phase close, and Phase 2 has three releases (`v0.3.0`, `v0.4.0`,
`v0.5.0`). This plan carries the first half. The patch/minor rule from the
`v0.2.0` plan still applies:

| | Patch (`v0.2.x`) | Minor (`v0.3.0`) |
| --- | --- | --- |
| Risk | Drop-in; no schema, manifest, CLI, or API change | May add surface and documented semantics |
| Contents | A defect that loses or corrupts work, or that a user hits today | New capabilities, new evidence, corrected docs |
| Evidence | A regression test that fails before and passes after | Scripted drills plus the release notes |
| Reversible by | Swapping the binary back | Swapping the binary back, if no migration ships |

Applying the rule: **no patch release is required.** None of the items above
loses accepted work. Two are outright documentation defects (`OT-001`,
`OT-005`) and one is a slow resource leak a user can already work around
(`otter release --keep`, `--list --all --prune`), so none justifies decoupling.
They ride with the code that makes them true, which is also what the `v0.2.0`
outlook already committed to. If an operator needs corrected retention SQL
before this release lands, a documentation-only `v0.2.x` patch is available, but
the corrected SQL is superseded by the built-in retention in the same release,
so the default is to let it ride.

**Goal: no migration ships.** Nothing planned here needs a new column, so
upgrade and downgrade stay a binary swap — the same property `v0.2.0` had. If a
workstream discovers it needs one, that is a decision to raise explicitly, with
the downgrade path stated.

*Outcome: the goal did not hold, through work that landed outside these
workstreams.* `0011_job_terminology` and `0012_job_schedules` shipped between
`v0.2.0` and this release, so an upgrade runs migrations and a rollback is a
restore. The decision that was promised in that case is recorded: the downgrade
path is stated in `operations.md` §Upgrades, enforced by the schema guard this
release adds, and asserted by the `downgrade-refusal` drill.

## WS1 — Automatic retention for runs and logs

**Theme.** Run logs are the only unbounded growth in the system, and the shipped
remedy is a documented SQL job that fails at runtime.

### Detail

`runs.LogStore.DeleteOlderThan` (`internal/runs/logs.go:280`) already deletes
log rows older than a cutoff, but its only caller is a test
(`internal/runs/runs_test.go:541`). There is no retention path for `runs` rows
at all: `Store.DeleteByJob` (`internal/runs/runs.go:227`) is identity
teardown, not retention.

Mirror the capture plumbing, which already solves the hard parts:

- `Daemon.runCaptureRetention` (`internal/daemon/inspection_api.go:201`) runs a
  ticker and calls `expireCapture`, which loops `ExpireOlderThan(ctx, cutoff, 50)`
  in bounded batches so one sweep cannot hold the database's single connection.
  `ExpireOlderThan` (`internal/inspection/store.go:616`) takes one transaction
  per run. Run retention must have the same shape.
- Configuration belongs beside `CaptureRetention` in
  `internal/config/daemon.go:58`, as `--log-retention` and `--run-retention`
  (environment variable plus flag, following the file's existing pattern).

Decisions this workstream must record:

1. **Default is 0 (retain forever).** Capture retention has a safe 7-day default
   because it keeps the summary, so an expired recording is still
   distinguishable from an empty one. Log lines have no summary fallback: once
   deleted, the run's output is gone. Automatically deleting run history in a
   minor release is a destructive default change, so the built-in retention is
   opt-in and the docs say so.
2. **Non-terminal work is never deleted.** A run in `queued`, `running` or
   `retrying` is live work and its logs may still be written.
3. **A retry chain is deleted as a unit or not at all.** While any attempt in a
   chain is non-terminal, no attempt in that chain is eligible. A run's
   `run_logs` are deleted with the run: the schema declares no foreign keys
   (`migrations/0001_init.sql:21`), so deleting a parent row would otherwise
   orphan its logs silently.
4. **Capture rows go too.** `inspection.Store.DeleteForRun`
   (`internal/inspection/store.go:568`) already exists; a deleted run must not
   leave its capture behind.
5. **The evidence revision stays true.** `internal/runs/timeline.go:142` states
   that the only deletion paths are `DeleteForRun`, `DeleteOlderThan` and the
   per-job cascade, and the timeline's O(1) evidence revision depends on
   that claim. A new bulk path either reuses `DeleteOlderThan` or is added to
   that list with a test that pins the invariant.
6. **Retention is visible.** Log one `logs_retained` / `runs_retained` line per
   sweep with the cutoff and the counts removed, so an operator can see the
   window is live rather than guessing.

`OT-001` is fixed as part of this: rewrite
`operations.md` §"Log rotation and run-log retention" (`478`–`554`) around the
new flags, keep the SQL as the manual alternative, and correct `queued_at` to
`created_at` in all three examples (the per-run delete at `511`, the run
history delete at `533`, and the weekly cron line at `553`). The cron example
also needs `run_logs.origin` (`migrations/0008_run_logs_origin.sql`) reconciled
with its claim to delete "including runtime annotations".

### Acceptance

- A test seeds log rows and terminal runs past the cutoff, plus a non-terminal
  run and a live retry chain inside it, and asserts retention removes exactly the
  former, never the latter, and is idempotent on a second pass.
- A daemon started with no retention flags deletes nothing, asserted as a
  regression against accidental data loss.
- `DeleteOlderThan`'s only caller is no longer a test.
- The three corrected SQL examples execute against a freshly migrated database;
  a test can run them to prove it.
- `--log-retention` and `--run-retention` are documented in `operations.md` and
  `README.md`, including that 0 is the default.

### Out of scope

Daemon-side release-directory retention (`OT-010`, `v0.4.0`). Admission bounds,
backpressure, and the supported-load envelope (`v0.5.0`).

## WS2 — Release retention and deploy pruning

**Theme.** The release directory only ever grows. `otter release --keep N`
prunes correctly, but nothing passes it, and `otter deploy` is the one path an
operator expects to converge.

### Detail

`release.Manager.Retain` (`internal/release/stage.go:261`) already implements the
right safety rule: it never removes the active release, never removes the newest
inactive one (so rollback always has a target), and protects any digest the
caller marks as referenced. `App.pinnedReleases` (`internal/cli/release.go:646`)
supplies the referenced set from runs in `queued`, `running` or `retrying`. The
machinery is sound; the gap is who calls it.

1. **Deploy must prune.** `internal/deploy/render.go:368` runs
   `$CLI release --jobs ... --data ... <dir>` with no `--keep`, and
   `App.releaseOne` only prunes when `keep > 0`
   (`internal/cli/release.go:397`). `operations.md:375` already tells the
   operator that "[n]othing removes them unless you pass `otter release --keep
   N`", which is the honest description of today's behavior and the sentence
   this workstream changes. Add a keep value to the deploy flags
   (`internal/deploy/config.go`, alongside the other `StringVar`/`BoolVar`
   registrations) with a bounded default — proposed `3`, so a deploy keeps the
   active release, one rollback target, and one spare. A deploy is the moment
   convergence is expected, so the default belongs there rather than in the
   release command.
2. **Pinning must gate every prune, and "no pins" must never mean "prune".**
   `pinnedReleases` returns `nil` when the database is missing or unreadable
   (`internal/cli/release.go:647`). Today that is only *survivable* because
   `Retain` independently keeps the active and newest inactive release. Once
   retention is automatic, an unreadable database must fail the prune closed
   with a clear message instead of proceeding on partial information. Record the
   rule: **a prune runs only with a readable pin set.**
3. **Enumerate the prune paths and make them agree.** They are
   `otter release --keep`, the deploy release step, and
   `otter release --list --all --prune --apply`. The first two already share
   `Retain`; the third is different in kind — `pruneOrphanReleases`
   (`internal/cli/release.go:751`) removes directories with no registered
   identity, which no run can be bound to. Confirm that distinction explicitly
   and leave it, rather than folding it into the pinned path.

`OT-002` is this design gate: every prune path consults pinning before it
removes anything, and the decision is written down rather than implied by the
one call site that happens to get it right.

### Acceptance

- A deploy test asserts old releases are pruned to the configured keep, and that
  the active release, the rollback target, and every digest held by a
  non-terminal run survive.
- A test asserts a prune refuses when the registry/database cannot be read,
  rather than proceeding with an empty pin set.
- `otter deploy --help` documents the keep behavior, and `operations.md` and
  `deploy.md` state what a deploy removes and what it always keeps.
- `OT-002` and `OT-003` are retired from [open-work.md](open-work.md).

### Out of scope

The daemon-side pinning check before automatic retention (`OT-010`, `v0.4.0`),
and any automatic release retention on a timer. `v0.3.0` prunes releases only
when an operator runs a release or a deploy.

## WS3 — Migration visibility

**Landed.** `Migrate` returns the migrations it applied
(`internal/database/migrate.go`) and `otterd` logs one `migration_applied` per
entry, or `migration_failed` naming the migration
(`internal/daemon/migrations.go`). No `description` column was added: `name` is
the description, and the `operations.md` upgrade example now shows the emitted
field. See `OT-005` in [open-work.md](open-work.md); tests in
`internal/database/database_test.go` and `internal/daemon/migrations_test.go`.

**Theme.** The ops guide tells an operator to watch `migration_applied` on
upgrade; the migrator has no logger and never emits it.

### Detail

`database.Migrate` (`internal/database/migrate.go:25`) applies each pending
migration inside its own transaction and records
`(version, name, applied_at)` in `schema_migrations`. It takes no logger and
returns only an error, so a successful upgrade is silent.

Shape the fix as the smaller of the two options `OT-005` names:

- **Ship the log line.** Have `Migrate` return what it applied — a
  `[]{Version, Name}` — and let `otterd` log one `migration_applied` at `info`
  per migration, and nothing when none were pending. A failure continues to
  abort startup (the error already propagates), but logs `migration_failed` with
  the version and name before returning.
- **Do not add a `description` column.** The example at `operations.md:702`
  invented one. `schema_migrations.name` is already the description, so the
  documented example is what changes, not the schema. This keeps the
  no-migration goal.
- "Stop promising one" is rejected: an upgrade is exactly when an operator needs
  to know the schema moved.

### Acceptance

- A test asserts one `migration_applied` record per pending migration on a first
  start, none on a second start (idempotence), and `migration_failed` on a
  broken migration.
- The `operations.md` §Upgrades example (`694`–`704`) matches the emitted JSON
  field for field, and the upgrade walkthrough still reads correctly against it.

### Out of scope

A migration downgrade tool and the published downgrade policy (`v0.4.0`).
Reporting the schema version through `/health` is a candidate for WS4, not a
commitment here.

## WS4 — Operate unattended: queue age, depth, freshness, storage

**Landed.** The authenticated `/health` carries `queue` (oldest claimable age,
per-job depth, retrying count and next retry), `freshness` (per-job last success
and age) and `storage` (`db_bytes` and the data directory's disk figures);
`otter status` prints them; and `GET /v1/jobs` carries `last_success_at` so the
schedule column is one rendering of freshness instead of a run listing per job.
The unauthenticated liveness body is unchanged, field for field. See `OT-004` in
[open-work.md](open-work.md); tests in `internal/queue`, `internal/runs`,
`internal/daemon/health_test.go`, `internal/api` and `internal/cli`.

**Theme.** `/health` answers "how many?" and none of "how old?", "which
job?", "did it stop succeeding?", "is the disk filling?".

### Detail

`HealthResponse` (`internal/api/types.go:157`) carries `status`, `version`,
`uptime_seconds`, `jobs{total,valid,invalid}`, `queue_depth` (one
integer) and `runs` (a status→count map). Counts alone cannot distinguish a
healthy queue from one that has been stuck for a day.

Add, to the authenticated branch only — the unauthenticated liveness probe must
stay exactly as it is (`api/server.go:360`):

- **Queue age.** The oldest waiting item's age. `run_queue.created_at`
  (`migrations/0001_init.sql:58`) is the submission time and `available_at` is
  the backoff clock, so define age precisely: oldest `created_at` among rows with
  `available_at <= now`, with `retrying` runs counted separately because they are
  parked by design, not blocked by capacity. `operations.md:770` already explains
  that distinction to a reader; the endpoint should not contradict it.
- **Per-job depth.** `queue.DepthByJob`
  (`internal/queue/queue.go:216`) already computes this and is used only by
  `internal/queue/queue_test.go:369`. Expose it through `api.Backend`
  (`internal/api/backend.go:145`) and into the response.
- **Freshness.** `last_success_at` (and its age) per job:
  `MAX(finished_at)` where `status = 'succeeded'`. This is the signal that turns
  "the daemon is up" into "the schedule is working". Part of it already exists,
  but only as a client-side convenience: `otter jobs --schedule` renders
  a LAST RUN column by calling `ListRuns(limit: 1)` per job
  (`internal/cli/cli.go:435`), which shows the latest run's *status* and its
  `created_at`, not its `finished_at`, and only for cron jobs. WS4 makes
  freshness a daemon-computed, first-class field (last success, completion time,
  age) exposed consistently through `/health` and `otter status`, and keeps the
  schedule column as one rendering of it rather than a separate N+1 query.
  `JobView.NextRunAt` already exists (`api/types.go:52`); this is its
  missing counterpart.
- **Retry activity.** Count of `retrying` runs and the next `available_at`, so a
  retry storm is visible without reading logs.
- **Storage pressure.** Report `PRAGMA page_count * page_size` as `db_bytes`,
  and the data directory's free/total bytes via `syscall.Statfs`. Prefer
  daemon-side numbers so a remote operator sees them through the API; the docs
  currently make "alert when `otter.db` exceeds about 2 GB" a host-level check
  (`operations.md:813`), which a remote caller cannot perform.

Surface the same signals through `otter status`, which already prints queue
depth and per-status counts and formats `NextRunAt` (`internal/cli/cli.go:429`),
keeping the terminal/JSON convention the other commands follow.

Then bring `operations.md` §"Health checking" (`788`–`820`) in line: extend the
alerting table with age, per-job backlog, freshness and storage rows, and
fix the sample response at `802`, which currently shows version `0.4.1` — a
version that does not exist — and no new fields.

### Acceptance

- A test seeds a queue with a known old `created_at`, a retry parked in the
  future, and a succeeded run with a known `finished_at`, and asserts age,
  per-job depth, retry activity and freshness exactly.
- A test asserts the unauthenticated `/health` body is byte-for-byte the old
  shape: no new disclosure to the network.
- The documented example matches the real response shape.

### Out of scope

A Prometheus/metrics endpoint and time-series history. The roadmap is explicit
that "a custom dashboard is not required for this phase"; `/health` plus the
documented monitoring job is the deliverable.

## WS5 — Documentation honesty: the backlog

**Landed.** `operations.md` §"Backlog behavior" states all five points beside the
capacity section, with the troubleshooting entry pointing at it; the downtime
half links to `runtime-contract.md` §"Missed cron windows are not replayed" and
the release half to `architecture.md` §"What runs is the release, not the tree",
so there is one source of truth for each. See `OT-008` in
[open-work.md](open-work.md).

**Theme.** The answer to "what happens if a run exceeds its next scheduled
run?" runs opposite to intuition and is written nowhere.

### Detail

Document all five points from [open-work.md](open-work.md) §"Backlog behavior to
document":

1. Every cron occurrence becomes its own run, unconditionally; nothing is skipped
   because a previous execution is still going.
2. With the default `concurrency: 1`, runs serialize: a slow job builds a
   catch-up backlog rather than overlapping.
3. **Downtime skips; slowness accumulates.** Occurrences missed while the daemon
   was down are never replayed, but occurrences during uptime always queue.
4. A deep backlog executes the release bound at *submission*, not the newest
   release, so queued work can run older code than what is active.
5. Raising `concurrency` to clear a backlog produces genuinely concurrent
   executions of the same job.

Placement: points 1–3 and 5 belong in `operations.md` beside the capacity
section (`739`+) and its troubleshooting counterpart §"Runs pile up in the
queue" (`1024`), where the reader is already asking about worker limits. Point 4
belongs with the release explanation in `operations.md` §"Managed Python"
(`357`–`380`, which already states that a job executes its release
snapshot, not its source tree) and in `architecture.md`, because it is a
consequence of release binding.

Point 3 already exists as a promise in
[runtime-contract.md](runtime-contract.md) §missed cron windows. Link to the
contract rather than restating it, so there is one source of truth for the
guarantee and the ops guide carries the operational consequence.

### Acceptance

- `operations.md` states all five points, each traceable to code
  (`cronTick` enqueues unconditionally; admission has no depth bound).
- The release-binding statement agrees with `runtime-contract.md`; a reader
  cannot find two different answers.
- No claim is made about *changing* the behavior — this workstream documents it.

### Out of scope

Changing the behavior. The missed-occurrence/admission policy for a busy
job is `OT-007`, `v0.5.0`, and it is a product promise, not a doc fix.

## WS6 — The gate: drills and proof

**Landed (machine half).** `OT-011`'s scenario passed earlier and the contract was
promoted; the drills are scripted under `scripts/drill/` and run through
`make drill`, with `backup-restore`, `upgrade`, `downgrade-refusal`,
`secret-rotation` and `fresh-archive` added or wired here, each with a
`DRILL_SABOTAGE` mode that goes red. `operations.md` §"Operating drills" documents
the entry point, the inputs and the CI/pre-tag split, and the `drills` and
`release-config` CI jobs run them. The trust-boundary claims are asserted by
named tests rather than restated (see below). `docs/releases/v0.3.0.md` cites the
retry-binding scenario as the release notes require.

Two decisions this section left open, recorded rather than assumed:

- **Downgrade refusal needed code, not only a drill.** No schema-version check
  existed, so "the old binary refuses rather than corrupting" was not true.
  `database.Migrate` now returns `*SchemaTooNewError` for a database whose
  newest applied migration it does not embed, before applying anything.
- **Secret rotation stays restart-based.** The premise that the reload API
  already rotates credentials was wrong: `internal/secrets` is an environment
  provider, there is no `--secrets-file` and no snapshot, and `otter reload` does
  not re-read credentials. Implementing
  [secret-reload-implementation-plan.md](secret-reload-implementation-plan.md)
  is therefore its own workstream, not a drill. `secret-rotation` asserts the
  shipped truth — restart applies a rotation, `otter reload` does not, and a
  missing credential fails before Python — and `operations.md` §"Reloading jobs"
  now names that as one of the three things reload does not do.

**The gate ran, and its first verdict was NOT SATISFIED.** The independent
second-operator record is
[evidence/v0.3.0/2026-10-02-v0.3.0-gate.txt](evidence/v0.3.0/2026-10-02-v0.3.0-gate.txt):
all nine drills passed and eleven sabotage runs went red at the assertion that
names what they removed, but four defects in what the repository *says* meant the
release would have shipped a known-false instruction.

- **F1 (release blocker, product).** `otter start --detach` rebuilt the child
  argv from `--jobs`/`--data`/`--listen` plus passthrough, dropping every other
  flag the operator typed — including `--api-token`, so a runtime started with a
  token came up with its API unauthenticated while `--help` promised the flag was
  forwarded. Present since `v0.2.0`. Fixed: the detached path now builds its argv
  through `daemonArgs`, the same function the foreground path uses, with a
  regression test (`TestStartChildArgsForwardEveryFlag`) that fails on the old
  construction.
- **F2 (doc).** The release notes said a job reading `OTTER_INTEGRATION_*` "must be
  updated"; the executor exports both name sets deliberately, for immutable
  releases written before the rename. Corrected, and the plan's own rename note
  with it.
- **F3 (doc + evidence gap).** `operations.md` and the release notes claimed every
  drill documents a `DRILL_SABOTAGE` mode; `unit-caps` does not. Both corrected to
  "eight of the nine", naming the `UnitFile` render-test mutation as its mechanism,
  and the drill-level mode is tracked as `OT-030`.
- **F4 (doc).** The downgrade `migration_failed` example omitted the `applied` and
  `known` fields it actually emits. Corrected.

Two gate items were **NOT RUN** for want of a host, and are scoped out by decision
rather than left implied: the two-host clean restore
(`DRILL_CLEAN_HOST=1`, which refuses to fall back to the same-host drill) and
`scripts/assert-host-permissions.sh`. Both mechanisms were proven on real hosts in
Phase 0 — see

### OT-011 — retry and backlog release binding

`planRetry` (`internal/daemon/workers.go`) copies `release_digest` and
`release_source_dir`, and resolves the parent's `environment_digest`, but no test
references `ReleaseSourceDir`, and the contract currently states the retry half
as an explicit non-guarantee. Add the matrix scenario the roadmap already asks
for:

- Activate a newer release between a failed attempt and its retry, then assert
  the retry executed the *parent's* snapshot.
- For managed Python, assert the retry resolved the parent's environment digest.
- Add the retention case: a pending backlog keeps its digest through a prune.

Promote the guarantee in `runtime-contract.md` §"Retries and external effects"
from non-guarantee to guaranteed **only when this scenario passes**, and cite it
from `docs/releases/v0.3.0.md`.

### Scripted drills

Every drill below becomes a command a second operator can run, not a paragraph
they must interpret. Proposed shape: `scripts/drill.sh` with subcommands, wired
to a `make drill` target; each drill asserts its own outcome and exits non-zero
with the failing evidence.

- **Backup and restore.** `operations.md` §Backups (`384`–`434`) prescribes
  `sqlite3 .backup` and a restore procedure; no test executes it. The drill
  creates a workspace with a job and a succeeded run, takes a hot
  backup while the daemon is writing, restores onto a *different* empty data
  directory with a fresh daemon, and asserts run history, state, identity and
  releases survive and the daemon starts. The full checkpoint/upload feature in
  [host-recovery-implementation-plan.md](host-recovery-implementation-plan.md)
  is not required: `v0.3.0` promises a tested manual restore onto a clean host,
  not automated checkpoint capture.
- **Upgrade.** Seed a database at the previous schema, start the current daemon,
  assert it reaches the expected schema and (once WS3 lands) emits
  `migration_applied`, and assert the documented post-upgrade commands
  (`otter status`, `otter jobs`, `otter runs`) work.
- **Downgrade refusal.** Assert the documented behavior holds: an older binary
  against a newer schema refuses rather than corrupting
  (`operations.md:720`), and the pre-upgrade backup restores.
- **Secret rotation.** The reload API and `secret-reload-implementation-plan.md`
  exist. Verify by drill that rotating a secret and reloading applies it without
  a restart, and state exactly what a child already running observes.
- **Deployment failure recovery.** A deploy that fails mid-convergence leaves
  the previous release active. Verify the claim against the deploy tests and add
  the drill step.
- **Fresh-host first success.** `scripts/smoke.sh` proves
  init→validate→release→run in a temp workspace with a locally built binary.
  The gate needs the same loop from a **published archive** on a host with no
  checkout: install `otter_<version>_linux_amd64.tar.gz`, then init, validate,
  release, run, inspect state, stop. Add it as a drill step or a CI job whose
  defining property is that no source-checkout tooling is involved.

### Trust-boundary verification

`security.md` already documents the model — host-user privileges, no tenant
isolation, constant-time token comparison, redaction, `?token=` exposure. Verify
rather than rewrite: assert the file modes the docs claim, assert an
unauthenticated `/health` discloses only status/version/uptime, and assert a
scoped webhook or per-run token cannot read another job's data. Correct
`security.md` wherever observation disagrees with it.

Outcome: each claim already had an assertion, and the pass mapped them rather
than adding a parallel check — the verified claims and their evidence are:

| Claim | Asserted by |
| --- | --- |
| Data directory is owner-only (`0700`) | `TestOpenCreatesDirectoryAndFile` (`internal/database/database_test.go`), plus `scripts/assert-host-permissions.sh` on a deployed host |
| A non-loopback bind without a token is refused | `TestValidateRefusesPublicListenWithoutToken`, `TestListenIsLoopback` |
| Unauthenticated `/health` carries only status, version, uptime | `TestHealthHidesCountersFromUnauthenticatedCallers` (exact field set) |
| A per-run token cannot read another job's run, logs or state | `TestRunTokenScopes` |
| A webhook token authorises only its own job's hook and is not recorded | `TestWebhookAuthentication` |
| Deployed env files are root-owned `0600` inside a `0700` directory | `scripts/assert-host-permissions.sh` (+ its 48-case suite in `make test-shell`); `internal/deploy` writes them under `umask 077` |

One documentation gap was closed rather than a falsehood corrected: the local
workspace's `otter.env` mode was unspecified. `security.md` §Filesystem

## Exit gate

The roadmap states it verbatim: **a second operator completes the operating
drills without author intervention.** Concretely, someone who did not build Otter
must be able to:

1. install from a published archive on a fresh host;
2. `init` → `validate` → `release` → `run` → inspect state;
3. diagnose a seeded failure using the timeline, logs and captured requests;
4. rotate a secret;
5. upgrade across a schema change, and observe it;
6. restore a backup onto a clean host.

using published instructions alone. The release ships with the drill record, the
corrected documents, the passing retry-binding scenario, and
`docs/releases/v0.3.0.md`. If a drill fails, the release does not ship with a
known-false instruction in it.

This is a **minor** release, but two of the assumptions this plan was written
under did not hold, and both are stated in
[`docs/releases/v0.3.0.md`](releases/v0.3.0.md) before anything else:

- **Two migrations ship** (`0011_job_terminology`, `0012_job_schedules`), so an
  upgrade is not reversible by swapping the binary back. The downgrade path —
  restore the pre-upgrade backup — is stated in `operations.md` §Upgrades, and
  this release adds the schema guard that enforces it.
- **The `integration` → `job` rename is public.** `integration_id` becomes
  `job_id` in CLI and HTTP JSON, and `OTTER_INTEGRATIONS_DIR` / `--integrations`
  are no longer read. Child processes and the embedded SDK get the new
  `OTTER_JOB_ID`/`_NAME`/`_DIR` **and keep** the old
  `OTTER_INTEGRATION_ID`/`_NAME`/`_DIR` names, deliberately, so a job inside an
  immutable release written before the rename keeps working. Every manifest field
  is unchanged. The breaking half is the JSON keys and the daemon-configuration
  names, not jobs.
- The `/health` additions are additive fields on the authenticated response, and
  `v0.4.0` is where the envelope is frozen — so they are documented as additions,
  not as a moving target.

## Release checklist

Applies to this release.

1. Every fix has a regression test that failed before it.
2. `make test`, `make smoke` and the drills pass locally and in CI.
3. `gofmt`/`go vet` are clean; the release-config and lint jobs pass.
4. `docs/releases/v0.3.0.md` states user-visible behavior, not "fixed bug"; the
   tag publishes it as the GitHub release body.
5. Every claim the release makes is true in the shipped artifact — re-read the
   relevant doc against the behavior, do not assume.
6. `CHANGELOG.md` links the new notes, and [open-work.md](open-work.md) retires
   the `OT-` IDs this release closed (`OT-001`–`OT-006`, `OT-008`, `OT-011`,
   leaving `OT-007` at `v0.5.0` and `OT-010` at `v0.4.0`).
7. Two migrations shipped (`0011`, `0012`) rather than none, so the downgrade
   path is stated in `operations.md` §Upgrades and enforced by the schema guard;
   `downgrade-refusal` asserts it, and `docs/releases/v0.3.0.md` carries the
   upgrade and rollback steps.
8. Tag only when the exit gate passed with a named second operator. The version
   number means the gate passed, not that the work is finished.
